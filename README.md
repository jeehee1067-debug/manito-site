# 송년회 마니또 사이트

송년회 4주 전부터 진행하는 마니또 미션 사이트. 미션 배정, 인증 코드, 받는 사람 인증, 주간 단서, 용의자 보드, 최종 지목, 익명 투표, 응모권 집계, 송년회 현장 추첨까지 한 곳에서 한다.

- 프런트엔드: React 18 + Vite 5
- 호스팅: GitHub Pages (방탈출과 같음, `main`에 올리면 자동 배포)
- 백엔드: Firebase 무료 요금제(Spark) — Authentication(메일 주소/비밀번호), Firestore
- 서버 코드(Cloud Functions)는 쓰지 않는다. 비밀 유지는 전부 `firestore.rules`(보안 규칙)로 처리한다.

## 방탈출(office-escape)에서 가져온 것

| 가져온 것 | 이유 |
|---|---|
| 화면 디자인 | GBA/포켓몬 스타일 색, 테두리, 버튼, 대사창, 로고를 방탈출 `style.css` 값 그대로 따랐다. |
| 참가자 캐릭터 4종 | 방탈출 `assets/img/char/p1~p4.png`를 `public/char/`에 복사. 내 프로필에서 고르고, 내 대상·용의자 보드·결과 발표에 나온다. |
| 파트장님·PL님 캐릭터 | 방탈출 `assets/img/char/boss1~4.png`(김주헌·김진석·윤지혜 파트장님, 손승준 PL님)를 `public/char/`에 복사. 로그인 화면 주인공으로 나온다(연말에는 크리스마스 소품을 얹은 그림). |
| 근무지 구분(SR3/S1L) | 대상이 다른 근무지면 직접 가지 않아도 되는 미션 카드만 나온다. 배정은 기본이 근무지 상관없이(다른 근무지끼리도 짝), 필요하면 같은 근무지끼리만으로 바꿀 수 있다. |
| GitHub Pages 호스팅 | 사내망에서 열리는 것이 이미 확인된 방식. Firebase Hosting의 하루 전송량 한도(360MB)도 피한다. |
| 갈무리 글꼴(jsDelivr) | 방탈출과 같은 글꼴이고, jsDelivr는 사내망에서 열리는 것이 확인됐다. 본문은 기기 기본 글꼴이라 외부 다운로드가 없다. |
| Firebase 설정을 코드 파일에 두는 방식 | 방탈출 `net.js`처럼 `src/firebase.config.js`에 둔다. 공개돼도 되는 값이고 보호는 보안 규칙이 맡는다. |
| "처음 들어온 사람이 운영자" 방식 | 방탈출의 관리자 비밀번호 고정 방식과 같은 발상. 참여자에게 링크를 주기 전에 운영자가 먼저 접속해야 한다. |
| 배포 전 점검 스크립트 습관 | `npm test`가 배정·응모권·추첨을 확인하고, 배포 워크플로가 테스트를 통과해야 배포한다. |

가져오지 않은 것: 방탈출의 기기별 임시 ID 방식(로그인 없음)은 쓰지 않았다. 마니또는 누가 누구를 맡았는지 숨겨야 해서 계정 로그인(Firebase Authentication)이 필요하다. 데이터베이스도 방탈출의 Realtime Database 대신 Firestore를 쓴다.

## 사내망 확인 (배포 전 꼭)

방탈출로 사내망에서 열리는 것이 확인된 곳: `github.io`, `cdn.jsdelivr.net`, `www.gstatic.com`, `*.firebasedatabase.app`.

이 사이트는 여기에 더해 아래 곳을 쓴다. **사내 PC와 사내 와이파이 휴대폰에서 각각 가입 한 번 해 보고** 되는지 확인할 것.

- `identitytoolkit.googleapis.com`, `securetoken.googleapis.com` (로그인)
- `firestore.googleapis.com` (데이터)
- `프로젝트ID.firebaseapp.com` (비밀번호 재설정 메일의 링크가 여는 페이지)

비밀번호 찾기도 한 번 해 볼 것. 재설정 메일은 `noreply@프로젝트ID.firebaseapp.com`에서 오는데, 회사 메일이면 차단되거나 스팸함으로 갈 수 있다. 사내망에서 링크가 안 열리면 휴대폰 데이터로 열어도 된다.

막혀 있으면 가입 화면에 "로그인 서버에 연결하지 못했어요"가 뜬다. 그 경우 데이터 쪽은 방탈출처럼 Realtime Database로 옮길 수 있지만, 로그인 없이는 짝 비밀을 지킬 수 없어서 설계를 다시 정해야 한다.

## 처음 설정

1. [Firebase 콘솔](https://console.firebase.google.com)에서 새 프로젝트를 만든다. 방탈출(`s1fa-escape`)과 데이터가 섞이지 않게 별도 프로젝트를 추천.
2. Authentication → 로그인 방법 → **이메일/비밀번호** 사용 설정(아래 "이메일 링크"는 끈 채로). 참여자는 실제 메일 주소로 가입하고, 비밀번호를 잊으면 로그인 화면의 "비밀번호를 잊었어요"로 재설정 메일을 받는다. Authentication → 템플릿에서 템플릿 언어를 한국어로 해 두면 좋다(앱도 한국어로 요청한다).
3. Authentication → 설정 → 승인된 도메인에 `계정명.github.io` 추가.
4. Firestore Database 만들기 (프로덕션 모드, 서울 `asia-northeast3` 권장).
5. 프로젝트 설정 → 내 앱 → 웹 앱 추가 → 설정값을 `src/firebase.config.js`에 붙여넣는다.
6. 보안 규칙 게시: Firestore → 규칙 탭에 `firestore.rules` 내용을 붙여넣고 게시. (터미널이 편하면 `firebase deploy --only firestore:rules`)
   **`firestore.rules`가 바뀔 때마다 다시 게시해야 한다.** 게시를 잊으면 운영 화면 맨 위에 "게시된 보안 규칙이 지금 사이트와 맞지 않아요" 경고가 뜬다(규칙의 `rulesVersion`과 `src/lib/constants.js`의 `RULES_VERSION`을 맞춰 보는 방식).
7. 로컬 실행
   ```
   npm install
   npm run dev
   ```
   Firebase 프로젝트 없이 화면을 점검하려면 `npm run dev:emu` (Java 21 이상 필요). 내 PC의 Firebase 에뮬레이터(로그인·Firestore)에 붙어서 뜨고, 데이터는 끄면 사라진다. 처음 실행할 때 에뮬레이터 파일을 내려받는다.
8. GitHub Pages 배포: 저장소 Settings → Pages → Source를 **GitHub Actions**로 바꾼 뒤 `main`에 push. 주소는 `https://계정명.github.io/저장소명/`.

## 운영 순서

운영 탭의 "다음 단계로" 버튼으로 진행한다. **단계는 되돌릴 수 없다**(보안 규칙으로 막혀 있음).

미션 진행을 시작하기 전에 전원이 가입했는지 확인할 것. 가입 안 한 사람이 있으면 시작 확인창에 이름이 나온다. 그 사람의 마니또는 인증을 받을 수 없어 미션 응모권이 0장이 되므로, 참여하지 않을 사람은 명단에서 지우고 다시 배정한 뒤 시작한다.

| 단계 | 운영진 | 참여자 |
|---|---|---|
| 0 준비 | 사이트 주소 끝에 `?setup`을 붙여 들어가 "운영자·공동 운영자 계정 만들기"로 운영자 계정 생성 → 명단 입력(이름,근무지,파트) → 배정 방식 선택 후 배정("짝 현황" 표에서 결과 확인) → 이름별 초대 코드 개별 전달 → 공동 운영자 한 명 이상 지정(아래 "운영자와 공동 운영자") | 초대 코드로 가입, 캐릭터 고르기, 프로필 6문항 작성, 규칙 탭 읽기 |
| 1 미션 진행 | 주차(1~3) 올리기, 매주 금요일 "단서 2개 공개"(주차마다 2개까지, 파트 순위도 같이 발표됨), 공지로 마감 안내, "짝 현황" 표로 주차별 진행 챙기기, 인증 0건인 사람 알림, "받은 게 없어요" 신고를 주차별로 확인(받았음·못 받음), 내용 없는 인증 무효 처리, 더 참여 못 하는 사람은 "중도 이탈" 표시 | 미션 카드 고르기 → 수행 → 완료 알리기(완료한 주차에는 "쪽지 더 보내기") / 받은 코드 입력 + 후기 20자 이상 / 받은 게 없으면 "받은 게 없어요" |
| 2 최종 지목 | 운영 탭에서 지목 안 한 사람 확인("짝 현황" 표에 누구를 지목했는지와 정답 여부가 나온다). 지목을 안 하면 그 사람의 마니또가 은신 2장을 받으니 마감 전에 알릴 것 | 용의자 보드에서 최종 지목 |
| 3 투표 | 수상 제외·중도 이탈 표시를 먼저 끝내고 "투표 카드 만들기"(수상 대상이 아닌 마니또는 카드에서 빠진다), 카드별 운영진 평가(0~10) | 익명 카드 Top 3 투표 |
| 4 집계 | "집계 전 확인" 표 처리(완료를 알렸는데 인증이 없는 주차를 두 사람에게 확인하고 주차별로 "받았음" 또는 "못 받음") → 수상 제외·중도 이탈 표시 마무리 → "집계하기", 베스트 후기상 선택. **집계해야 공개 단계로 넘어갈 수 있다** | 대기 |
| 5 공개 | 결과 탭에서 4등 → 3등 → 2등 → 대추첨 순서로 추첨. 한 번 뽑은 결과는 다시 뽑거나 바꿀 수 없다(공개 단계에서는 다시 집계도 안 된다) | 결과 확인 |

명단 입력 형식은 한 줄에 한 명, `이름,근무지,파트`(근무지·파트는 생략 가능, `이름,,파트`도 됨). 근무지는 `SR3`, `S1L` (`src/lib/constants.js`의 `LOCS`에서 바꿀 수 있음). 명단 표에서 근무지·파트를 눌러 바꿀 수도 있다. "파트"는 실제 소속 파트이고, **같은 파트끼리 짝 피하기·파트 단서·파트 순위·투표 카드 숨김**에 모두 쓰인다. 파트를 비워 두면 그 사람은 누구와도 짝이 될 수 있고 파트 순위에서 빠진다. 배정한 뒤 파트를 고쳤다면 다시 배정해야 반영된다.

참여 인원은 54명(부서 56명 중 운영자와 PL님 제외)을 기준으로 했다. 인원 수는 코드에 고정돼 있지 않고 명단에 넣은 사람 수대로 동작한다.

### 운영자와 공동 운영자

운영자와 공동 운영자는 **마니또에 참여하지 않는 계정**이다. 명단에 넣지 않고, 초대 코드로 명단에 연결할 수도 없다(보안 규칙이 막는다). 반대로 명단에 연결된 계정(참여자)은 운영자가 될 수 없다. 참여하지 않기 때문에 누가 누구의 마니또인지, 주차별 진행, 최종 지목을 처음부터 볼 수 있다(운영 탭 "짝 현황").

공동 운영자 지정 방법:

1. 지정할 사람이 사이트 주소 끝에 `?setup`을 붙여 들어가 "운영자·공동 운영자 계정 만들기"로 계정을 만든다(이미 계정이 있으면 로그인만 하면 된다. 단, 참여자로 연결된 계정은 안 된다).
2. 이미 운영자가 있으므로 그 계정은 "연결 전" 화면으로 가고, 거기에 **계정 번호**가 나온다. "계정 번호 복사"로 복사해 운영자에게 보낸다. 초대 코드는 입력하지 않는다.
3. 운영자가 운영 탭 맨 아래 "공동 운영자"에 계정 번호와 메모(누구 계정인지)를 넣고 지정한다. 그 계정 화면이 바로 운영 화면으로 바뀐다.

권한을 빼면 그 계정은 다시 "연결 전" 화면으로 돌아간다. 예전 방식(참여자를 공동 운영자로 지정)으로 남아 있는 계정이 있으면 "공동 운영자" 패널에 경고가 뜨니 권한을 빼고 별도 계정을 지정한다.

## 규칙 요약 (코드에 반영된 것)

- 배정: 한 바퀴로 이어지는 원형 배정. 자기 자신·같은 파트·서로 마니또인 쌍은 생기지 않는다. 운영 화면에서 두 방식 중 고른다.
  - **근무지 상관없이(기본)**: 다른 근무지끼리도 짝이 된다. 대상이 다른 근무지면 쪽지·플레이리스트·공범 섭외처럼 직접 가지 않아도 되는 카드만 나온다.
  - **같은 근무지끼리만**: 근무지별로 원이 따로 생긴다. 3명 미만인 근무지는 큰 근무지 원에 합친다. 추리 보드에서 다른 근무지가 후보에서 빠진다.
  - 같은 파트를 완전히 피하려면 (근무지 모드에서는 근무지마다) 가장 큰 파트가 인원의 절반 이하여야 한다. 넘으면 같은 파트 짝을 되도록 적게 만들고 운영 화면에 경고를 띄운다. 이 경우(`config.partExcluded = false`) 추리 보드는 내 파트를 후보에서 빼지 않는다.
  - 만드는 방법: 무작위로 섞어 맞을 때까지 반복하는 방식은 파트처럼 큰 묶음에서는 사실상 성공하지 못해서(18명 × 3파트 기준 20만 번 중 0번), 조건에 맞는 원을 먼저 만든 뒤 조건을 깨지 않는 자리 맞바꾸기로 섞는다(`src/lib/assign.js`).
  - 추리 보드는 처음부터 내 파트 사람을 후보에서 뺀다. 파트가 둘뿐이면 마지막 파트 단서는 새 정보가 되지 않는다(처음부터 다른 파트로 정해져 있음).
- 미션: 1·2주차는 쉬움·보통·도전 카드 3장 중 1장 선택, 3주차는 전원 칭찬 카드. 미션마다 4자리 인증 코드. 난이도마다 "다른 카드 보기"로 같은 난이도의 다른 카드를 볼 수 있다. 카드 고르기·완료 알리기·인증은 **열린 주차까지만** 된다(화면뿐 아니라 보안 규칙도 막는다). 지난 주차는 미션 진행 기간 안이면 늦게라도 할 수 있다.
- 쪽지 더 보내기: 완료를 알린 주차에는 쪽지를 더 보낼 수 있다(주차마다 5건까지, `EXTRA_NOTES_MAX`. 개수는 화면에서만 센다). "3일 연속 매일 다른 응원 쪽지" 카드는 첫날 완료를 알린 뒤 이것으로 이어서 보낸다. 완료 표시와 응모권에는 영향이 없다. "대상 이름 삼행시 쪽지 보내기" 카드는 도전에서 보통으로 옮겼다.
- 미션 비용: 간식·음료·선물처럼 본인 돈이 드는 카드는 "소액 비용"으로 표시하고 건당 5천원 이하를 권장한다(`SPEND_GUIDE_WON`). 모든 난이도에 돈이 안 드는 카드가 있어서 무비용으로도 같은 응모권을 받을 수 있다.
- 인증: 사진 없이 받는 사람이 코드 + 후기(20자 이상) 입력. 코드는 자기 마니또가 보낸 것만 통과. 인증하면 인증 문서(`redemptions`)와 익명 피드 글(`feed`)이 한 묶음으로 만들어진다.
- 익명 피드: `feed` 문서에는 받는 사람 정보도 코드도 없다(주차·후기·무효 여부·시각·감사 답장만, 문서 ID는 무작위). 인증 문서는 인증한 받는 사람, 그 코드를 가진 마니또, 운영자만 읽는다. 감사 답장은 글쓴이가 자기 피드 글에 한 번 붙이고, 마니또는 자기 미션의 피드 글에서 읽는다.
- 받은 게 없어요: 마니또가 완료를 알렸는데 받은 것이 없으면 받는 사람이 추리 보드에서 주차별로 알린다(1·2주차, 집계 전까지). 마니또 화면에도 알림이 뜬다. 운영자가 두 사람에게 확인하고 주차마다 **받았음**(마니또의 미션으로 인정) 또는 **못 받음**(인정하지 않고 받는 사람에게 그 주차 보상)으로 정한다. 신고가 없어도 집계 단계의 "집계 전 확인" 표에서 같은 확인을 할 수 있다(받고도 인증하지 않은 경우).
- 단서 문항: 6문항 중 4개는 고르기(주로 마시는 음료, 점심, 출근 시간, 출퇴근 방법 — 동료가 실제로 관찰할 수 있는 것), 2개는 직접 쓰기(2자 이상). 대충 쓰거나 한 글자로 넘길 수 없다. 문항·보기는 `src/lib/constants.js`의 `PROFILE_QUESTIONS`에서 바꾼다(행사 시작 전에만).
- 파트 단서: 최종 지목 단계가 열리면 "내 마니또의 파트"가 마지막 단서로 공개되고, 용의자 보드가 그 파트 사람으로 좁혀진다. 배정할 때 명단의 파트로 자동으로 만들어져서 거짓으로 바꿀 수 없고, 마니또가 접속을 안 해도 나간다. 인원이 적은 파트는 이 단서만으로 거의 드러난다(운영 화면이 파트별 인원을 보여 준다).
- 단서: 마니또의 프로필 답변이 운영자가 공개한 개수만큼만 보인다(매주 2개, 최대 6개). **주차마다 2개까지만** 공개된다(공개 개수 ≤ 2 × 주차. 같은 주에 두 번 누르는 실수를 화면과 보안 규칙이 막는다). 이미 공개된 단서 칸은 프로필에서 고칠 수 없다(대상이 본 단서가 나중에 바뀌지 않게, 보안 규칙도 같은 기준). 아직 공개 안 된 칸은 고칠 수 있고, 비어 있던 칸은 늦게라도 쓸 수 있다.
- 응모권: 미션 인증 1장(최대 3), 도전 미션 +1장(최대 2), 받는 사람 인증 입력 1장(최대 3), 끝까지 안 들킴 2장, 정답 지목 1장, 우승 파트 1장. 최대 12장.
  - 은신 2장은 **내 미션이 1건 이상 인증된 마니또만** 받는다. (조건이 없으면 아무것도 안 한 사람이 가장 안 들켜서 2장을 받고, 가입 안 한 사람까지 추첨 대상이 됐다.)
  - 도전 추가분은 **받는 사람이 직접 인증한 미션에만** 붙는다. 대상 불참이나 운영자 확인으로 인정된 미션은 미션 응모권 1장만 받는다.
  - 상대방 때문에 손해 보지 않게: ① 내 마니또가 미션을 안 보낸 주차, 그리고 완료를 알렸지만 운영자가 "못 받음"으로 확인한 주차는 인증 입력 대신 1장(인증 입력과 합쳐 최대 3장, 내 미션이 1건 이상 인증된 사람만). ② 완료를 알렸는데 인증이 없는 미션은, 대상이 불참(가입 안 함·중도 이탈)이거나 운영자가 "받았음"으로 확인하면 인증된 것으로 인정한다(운영자의 확인이 먼저다: "못 받음"이면 불참이어도 인정하지 않는다). ③ 확인이 없는 미인증 주차(대상이 참여 중)는 마니또도 받는 사람도 받지 못한다. 그래서 집계 전에 "집계 전 확인" 표를 꼭 처리한다.
  - 가입 안 한 사람, 중도 이탈, 수상 제외는 0장(추첨 대상 아님).
  - 정체를 알려주면 둘의 합계가 1장 줄어드는 구조는 미션이 1건 이상 인증된 마니또에게만 성립한다. 미션이 0건인 마니또는 잃을 은신이 없어서, 알려주면 받는 사람만 1장을 얻는다(확인되면 수상 제외로 대응).
- 파트 대항전: 파트별 미션 완수율로 순위를 매긴다.
  - 주간 순위("파트 순위" 탭): 파트원이 완료를 알린 미션 수 ÷ (가입한 파트 인원 × 열린 주차). 운영자가 "이번 주 단서 2개 공개"를 누를 때 같이 발표되고(`public/board` 문서), "파트 순위만 다시 발표"로 따로 갱신할 수도 있다. 미션 진행을 마감하고 최종 지목으로 넘길 때 마지막으로 한 번 더 발표된다. **실시간이 아니다.** 실시간이면 미션을 받은 직후 어느 파트 숫자가 올랐는지로 마니또의 파트가 드러난다.
  - 개인별 진행(누가 몇 개 했는지)은 본인과 운영자만 본다(보안 규칙). 참여자에게는 파트 합계만 보인다.
  - 최종 순위(집계): 받는 사람이 인증한(또는 운영자가 인정한) 미션 수 ÷ (가입한 파트 인원 × 3). 1위 파트(동률이면 모두)의 파트원은 응모권 +1장. **내 미션이 1건 이상 인증된 사람만** 받고, 불참·수상 제외는 받지 못한다. 불참자(가입 안 함·중도 이탈)는 파트 인원에서도 빠진다.
  - 한계: 주간 순위가 0%이거나 100%인 파트가 있으면 "미션을 받았으니 내 마니또는 0% 파트가 아니다" 같은 추리가 된다(파트 합계를 발표하는 한 피할 수 없음). 인원이 적은 파트는 한두 명에 따라 완수율이 크게 움직인다.
- 베스트 마니또: 완수율 30% + 전체 투표 50% + 운영진 평가 20%. 투표 카드는 사람마다 다른 순서·번호로 보이고, 자기 파트 카드는 빠진다(파트가 없는 사람은 전부 보인다). 파트 인원이 다르면 카드마다 볼 수 있는 사람 수가 달라서, 투표 점수는 표 수 그대로가 아니라 **표 수 ÷ 기대 득표**(그 카드를 볼 수 있었던 투표자가 보이는 카드 중에서 고르게 찍었을 때 받을 표 수)로 계산한다. 파트 인원이 모두 같으면 표 수 비교와 같다. 화면에서 고를 수 없는 표(내 파트 카드, 같은 카드 중복)는 세지 않는다. 동점이면 인증된 미션이 많은 쪽 → 투표 점수가 높은 쪽 → 운영진 평가가 높은 쪽 → 무작위.
  - 수상 대상이 아닌 마니또(가입 안 함·중도 이탈·수상 제외)는 투표 카드를 만들 때 빠진다. 카드를 만든 뒤에 제외된 사람의 카드는 집계에서 없는 것으로 본다: 그 카드에 간 표는 버리고, 그 카드가 표를 많이 받았어도 다른 사람의 투표 점수가 낮아지지 않는다.
- 추첨: 응모권 수에 비례. 2~4등끼리는 중복 당첨 없음, 대추첨은 전원 대상. 추첨 결과는 한 번 쓰면 덮어쓸 수 없다(화면은 서버의 지금 값을 확인하고 쓰고, 보안 규칙은 이미 있는 추첨 결과의 변경·삭제와 공개 단계의 재집계를 거부한다).
- 단계: 한 칸씩 앞으로만 넘어간다. 집계 결과가 없으면 공개 단계로 넘어갈 수 없다(화면과 보안 규칙).

## 운영 도구

- **규칙 탭**: 참여자에게 응모권·상품·단서·비용·지켜야 할 것·누가 무엇을 볼 수 있는지를 보여 준다. 숫자는 `prizes.js`·`constants.js`에서 가져온다(`src/pages/Rules.jsx`). 문장으로 적은 규칙은 `src/lib/scoring.js`와 같아야 한다.
- **공지**: 운영 탭에서 올리면 모든 참여자 화면 위에 보인다(마감 안내 등).
- **공동 운영자**: 참여하지 않는 계정을 계정 번호로 지정한다(위 "운영자와 공동 운영자"). 운영자가 자리를 비워도 주차·단서·단계 진행이 멈추지 않게 한 명 이상 지정해 둘 것.
- **짝 현황**: 운영 탭에 누가 누구의 마니또인지와 주차별 상태(카드 고름, 인증 대기, 받은 게 없다고 신고, 받았음·못 받음 확인, 인증됨, 인증 무효), 추가 쪽지 수, 최종 지목(정답·오답)이 표로 나온다. 운영자 화면에만 보이므로 화면을 다른 사람이 보지 않게 주의한다.
- **받은 게 없어요 신고**: 미션 진행~투표 단계에 신고된 주차가 표로 나온다. 두 사람에게 확인하고 "받았음" 또는 "못 받음"을 누른다(같은 버튼을 다시 누르면 취소).
- **최근 접속**: 미션 진행 현황 표에 사람별로 보인다. 받은 미션을 인증하지 않으면 그 사람의 마니또가 응모권을 못 받으므로, 오래 안 들어온 사람은 따로 알려 준다. 참여자 화면에도 "아직 인증하지 않은 미션 n건" 알림이 뜬다.
- **중도 이탈**: 더 참여할 수 없게 된 사람을 표시한다. 본인은 0장, 그 사람의 마니또와 그 사람이 맡은 사람은 위 보완 규칙으로 처리된다.
- **집계 전 확인**: 집계 단계에서 "인증이 없는 완료 알림" 표가 나온다(신고가 없던 것 포함). 주차마다 "받았음" 또는 "못 받음"으로 처리하고 집계할 것. 처리하지 않은 주차는 어느 쪽에도 응모권이 생기지 않는다(대상이 불참이면 자동으로 마니또의 미션으로 인정).
- **규칙 버전 경고**: 콘솔에 게시된 보안 규칙이 예전 것이면 운영 화면 맨 위에 경고가 뜬다. 그 상태에서는 인증·피드·배정이 거부되므로 바로 `firestore.rules`를 게시한다.

## 로그인과 같은 기기 사용

- 메일 주소 + 비밀번호로 로그인한다. 메일 주소는 본인의 연결 문서(`users/{uid}`)에만 저장돼 본인과 운영자만 볼 수 있다(다른 참여자는 못 봄). 내 프로필 화면에 로그인한 메일이, 운영 화면 명단·계정 연결 표에 이름별 "연결된 메일"이 표시된다. 규칙이 로그인한 계정의 메일과 같은 값만 받는다.
- 같은 기기를 여러 사람이 쓸 수 있다. 헤더에 지금 로그인한 사람이 "○○님 로그아웃"으로 보이고, 로그아웃 후 다른 사람이 자기 계정으로 로그인하면 된다. 사람이 바뀌면 화면 상태를 통째로 새로 만들어 앞 사람의 이름·데이터가 남지 않는다.
- 로그인 화면의 "이 기기에서 로그인 유지"를 해제하면 그 탭을 닫을 때 로그아웃된다(공용 기기용). 체크하면(기본) 로그아웃하기 전까지 유지된다.
- 비밀번호를 잊으면 "비밀번호를 잊었어요" → 메일의 링크에서 새 비밀번호를 정한다.
- **계정 연결 해제**(운영 화면, 준비 단계는 명단 표 / 미션 시작 후는 "계정 연결" 표): 다른 사람이 초대 코드로 연결했거나, 메일을 잘못 적었거나, 비밀번호를 찾을 수 없을 때 쓴다. 누르면 그 계정은 "연결 전"으로 돌아가 아무것도 못 읽고, 초대 코드가 새로 바뀐다(예전 코드는 못 씀). 새 코드를 본인에게 전달하면 새 계정(또는 같은 계정)으로 다시 연결되고 프로필·미션·인증 기록은 이어진다. 용의자 보드에서 지운 표시만 초기화된다.

## 무료 한도와 읽기 수

무료 요금제(Spark)는 Firestore 읽기에 하루 한도가 있다(알려진 값 5만 건, 한국 시간 오후 5시쯤 초기화). 넘으면 그날 남은 시간 동안 모두 데이터를 못 불러온다. 그래서 같은 내용을 덜 읽게 만들어 두었다(행사 규칙·화면 순서는 그대로).

- 명단: 참여자 화면은 54명 문서 대신 요약 문서 `public/roster` 1건(이름·근무지·파트)을 읽는다. 운영 탭을 열면 명단과 요약이 다를 때 자동으로 다시 쓴다(미션 시작 때도 한 번 더 씀). 운영 화면은 전체 명단을 그대로 읽는다.
- 캐릭터: 전원 것을 구독하지 않고 화면에 나온 사람 것만 읽어 두고, 10분이 지나면 다시 읽는다. 다른 사람이 캐릭터를 바꾸면 최대 10분 늦게 보인다.
- 피드: `feed` 문서를 최근 30건씩, "더 보기"로 30건 더. 감사 답장은 같은 문서에 들어 있어서 따로 읽지 않는다.
- 파트 순위: 발표 문서 `public/board` 1건과 내 진행 문서 1건만 읽는다(예전 "우리 팀" 탭은 팀원 수만큼 읽었다).
- 기기 저장소 캐시는 쓰지 않는다. 같은 기기를 여러 사람이 쓸 때 앞 사람 데이터가 기기에 남지 않게 하기 위해서다.

운영 화면은 짝 현황 때문에 배정·코드·미션·인증·신고·지목을 전부 구독한다(54명 기준 한 번 열 때 수백 건). 운영자 계정이 몇 개뿐이라 한도에는 영향이 작지만, 운영 화면을 여러 기기에 계속 띄워 두지는 말 것.

코드로 계산한 추정치(측정값 아님): 사이트 한 번 열기 약 130건 → 약 20건(내 미션 화면 기준), 피드 열기 최대 약 340건 → 약 30건. 추리 보드는 후보 캐릭터 때문에 처음 열 때 후보 수만큼 더 읽는다. 행사 중에는 Firebase 콘솔 → Firestore → 사용량에서 하루 읽기 수를 확인할 것.

## 비밀 유지 범위와 한계

- 외부인: 설정값이 공개라 누구나 Firebase 계정을 만들 수는 있지만, 초대 코드로 명단에 연결되기 전에는 단계 정보(config)와 초대 코드 하나 확인 말고는 아무것도 읽을 수 없고(명단·피드·결과 포함) 아무것도 쓸 수 없다(보안 규칙, `npm run test:rules`로 확인). 사이트 화면·코드는 GitHub 저장소에 쓰기 권한이 있는 계정만 바꿀 수 있으니 GitHub 계정에 2단계 인증을 켜 둘 것.
- 참여자: 남의 배정·코드·단서·쪽지·인증 문서·진행 상황과 명단 원본(연결된 계정, 수상 제외·중도 이탈 표시)을 읽을 수 없다(보안 규칙). 익명 피드 글에는 받는 사람 정보가 저장돼 있지 않다.
- 운영자·공동 운영자: 참여하지 않는 계정이라 짝·코드·미션 진행·인증·신고·지목을 **언제든** 읽는다. 쪽지 내용과 투표는 집계 단계(4)부터 읽고, 프로필 답과 단서는 읽을 수 없다. 운영자 계정은 명단에 연결할 수 없고, 명단에 연결된 계정은 운영자가 될 수 없다(보안 규칙). 운영 화면에는 짝이 그대로 보이므로 화면 공유·어깨너머 보기에 주의한다.
- 단, 다음은 막을 수 없다.
  - Firebase 콘솔에 접근할 수 있는 사람은 Firestore 데이터를 직접 볼 수 있다.
  - 운영자와 공동 운영자는 누가 누구의 마니또인지 안다. 운영자가 참여자에게 알려 주는 것은 기술적으로 막을 수 없다(믿을 수 있는 사람만 지정할 것).
  - 개발자 도구로 Firestore에 직접 요청을 보내면 내 진행 문서의 완료 수(주간 파트 순위에 쓰임, 열린 주차 수까지)는 실제보다 높게 적을 수 있다. 최종 순위와 응모권은 받는 사람의 인증으로 계산하므로 영향이 없다. 투표도 직접 요청으로 내 파트 카드를 적을 수는 있지만 집계에서 세지 않는다(파트가 입력된 경우). 응모권 핵심(인증 코드 검증, 인증 없는 피드 글, 단계 건너뛰기·역행, 안 열린 주차의 인증·완료·카드 고르기, 미션 난이도 바꾸기)은 규칙으로 막았다. 난이도는 완료 표시를 했거나 그 슬롯 코드가 이미 인증되면 바꿀 수 없고, 3주차 칭찬 슬롯에는 칭찬 카드만 들어간다. "쪽지 더 보내기"의 개수 제한(주차마다 5건)은 화면에서만 세므로 직접 요청으로는 더 보낼 수 있다.
  - 받는 사람이 실제로 받고도 "받은 게 없어요"로 알리거나, 마니또가 하지 않은 미션을 완료로 알리는 것은 사이트가 가려낼 수 없다. 그래서 운영자가 두 사람에게 확인하고 주차별로 정하게 했다.
- 재배정용 메모(`meta/assignment`)는 다시 배정할 때 지울 문서 목록이다(코드·사람 목록).
- 받는 사람 기준 코드(`receiverCodes`)는 배정할 때 같이 쓴다. 보안 규칙이 "이 피드 글이 그 사람의 실제 인증에 딸린 것인지" 확인하는 데 쓰고, 참여자는 읽을 수 없다. 예전 방식으로 배정된 자료에는 이 문서가 없는데, 미션이 시작된 뒤 운영 화면을 열면 자동으로 채워 넣는다.
- 다시 배정하면 배정 회차(`config.assignVer`)가 올라간다. 단서는 지금 회차 것만 읽을 수 있어 예전 마니또의 답이 남지 않고, 새 마니또가 앱을 열 때(내 미션 화면) 자동으로 새 대상에게 단서를 다시 보낸다. 새 마니또가 앱을 열기 전에는 받는 사람 화면에 "아직 마니또가 프로필을 안 채웠어요"로 보인다.

Firestore 에뮬레이터를 띄워 `firestore.rules`를 확인한다(Java 21 이상 필요). 두 종류다.

- 막아야 하는 것: 남의 배정·코드·단서·쪽지·프로필·진행 상황·인증 문서·명단 원본 읽기, 남에게 발급된 코드로 인증, 인증 없는 피드 글·남의 인증에 붙인 글, 안 열린 주차의 인증·완료 알림·카드 고르기, 단계 건너뛰기·역행, 집계 없는 공개, 주차당 2개를 넘는 단서 공개, 추첨 결과 덮어쓰기, 운영자 계정의 명단 연결과 참여자의 운영자 지정, 완료했거나 인증된 슬롯의 난이도 변경, 초대 코드 가로채기 등
- 앱이 실제로 보내는 요청이 거부되지 않는 것: 각 화면이 Firestore에 쓰는 값의 모양을 그대로 옮겨 적은 "앱 흐름" 테스트. **화면에서 쓰는 값(필드 이름·타입·길이)을 바꾸면 규칙과 이 테스트를 같이 고칠 것.**

GitHub Actions도 같은 순서(`npm test` → `npm run test:rules` → `npm run build`)로 돌린다. main은 통과해야 배포되고, 다른 브랜치는 테스트만 한다.

에뮬레이터로는 확인할 수 없는 것(실제 프로젝트에서 직접 확인할 것):

1. 규칙 게시가 오류 없이 끝나는지
2. 사내 PC·사내 와이파이 휴대폰에서 가입과 데이터 읽기·쓰기가 되는지(위 "사내망 확인")
3. 실제 Firebase 프로젝트 설정값(`src/firebase.config.js`)으로 로그인·가입이 되는지
4. 테스트 계정 2~3개로 운영자 설정 → 명단 → 배정 → 가입 → 미션 완료 → 코드 입력 → 단서 공개가 되는지 (같은 흐름을 `npm run dev:emu`로 로컬에서 먼저 볼 수 있다)
5. 운영 화면 맨 위에 규칙 버전 경고가 뜨지 않는지(뜨면 `firestore.rules`를 다시 게시)

## 운영자 계정 만들기 버튼

로그인 화면의 "운영자·공동 운영자 계정 만들기"는 사이트 주소 끝에 `?setup`을 붙여 들어갔을 때만 보인다(예: `https://jeehee1067-debug.github.io/manito-site/?setup`). 아직 운영자가 없는 프로젝트에서는 이 계정이 첫 운영자가 된다. 이미 운영자가 있으면 보안 규칙이 막아서 운영자가 되지 않고, 계정만 만들어져 "연결 전" 화면(계정 번호)으로 간다. 그 번호를 운영자가 "공동 운영자"에 넣어야 운영 권한이 생긴다.
