# 송년회 마니또 사이트

송년회 4주 전부터 진행하는 마니또 미션 사이트. 미션 배정, 인증 코드, 받는 사람 인증, 주간 단서, 용의자 보드, 최종 지목, 익명 투표, 응모권 집계, 송년회 현장 추첨까지 한 곳에서 한다.

- 프런트엔드: React 18 + Vite 5
- 호스팅: GitHub Pages (방탈출과 같음, `main`에 올리면 자동 배포)
- 백엔드: Firebase 무료 요금제(Spark) — Authentication(메일 주소/비밀번호), Firestore
- 서버 코드(Cloud Functions)는 쓰지 않는다. 비밀 유지는 전부 `firestore.rules`(보안 규칙)로 처리한다.

## 방탈출(office-escape)에서 가져온 것

| 가져온 것 | 이유 |
|---|---|
| 화면 디자인 | GBA/포켓몬 스타일 색, 테두리, 버튼, 대사창, 로고를 방탈출 `style.css` 값 그대로 따랐다. |
| 참가자 캐릭터 4종 | 방탈출 `assets/img/char/p1~p4.png`를 `public/char/`에 복사. 내 프로필에서 고르고, 내 대상·용의자 보드·우리 팀·결과 발표에 나온다. |
| 근무지 구분(SR3/S1L) | 대상이 다른 근무지면 직접 가지 않아도 되는 미션 카드만 나온다. 배정은 기본이 근무지 상관없이(다른 근무지끼리도 짝), 필요하면 같은 근무지끼리만으로 바꿀 수 있다. |
| GitHub Pages 호스팅 | 사내망에서 열리는 것이 이미 확인된 방식. Firebase Hosting의 하루 전송량 한도(360MB)도 피한다. |
| 갈무리 글꼴(jsDelivr) | 방탈출과 같은 글꼴이고, jsDelivr는 사내망에서 열리는 것이 확인됐다. 본문은 기기 기본 글꼴이라 외부 다운로드가 없다. |
| Firebase 설정을 코드 파일에 두는 방식 | 방탈출 `net.js`처럼 `src/firebase.config.js`에 둔다. 공개돼도 되는 값이고 보호는 보안 규칙이 맡는다. |
| "처음 들어온 사람이 운영자" 방식 | 방탈출의 관리자 비밀번호 고정 방식과 같은 발상. 참여자에게 링크를 주기 전에 운영자가 먼저 접속해야 한다. |
| 배포 전 점검 스크립트 습관 | `npm test`가 배정·응모권·추첨을 확인하고, 배포 워크플로가 테스트를 통과해야 배포한다. |

가져오지 않은 것: 방탈출의 기기별 임시 ID 방식(로그인 없음)은 쓰지 않았다. 마니또는 누가 누구를 맡았는지 숨겨야 해서 계정 로그인(Firebase Authentication)이 필요하다. 데이터베이스도 방탈출의 Realtime Database 대신 Firestore를 쓴다.

## 사내망 확인 (배포 전 꼭)

방탈출로 사내망에서 열리는 것이 확인된 곳: `github.io`, `cdn.jsdelivr.net`, `www.gstatic.com`, `*.firebasedatabase.app`.

이 사이트는 여기에 더해 아래 곳을 쓴다. **사내 PC와 사내 와이파이 휴대폰에서 각각 가입 한 번 해 보고** 되는지 확인할 것.

- `identitytoolkit.googleapis.com`, `securetoken.googleapis.com` (로그인)
- `firestore.googleapis.com` (데이터)
- `프로젝트ID.firebaseapp.com` (비밀번호 재설정 메일의 링크가 여는 페이지)

비밀번호 찾기도 한 번 해 볼 것. 재설정 메일은 `noreply@프로젝트ID.firebaseapp.com`에서 오는데, 회사 메일이면 차단되거나 스팸함으로 갈 수 있다. 사내망에서 링크가 안 열리면 휴대폰 데이터로 열어도 된다.

막혀 있으면 가입 화면에 "로그인 서버에 연결하지 못했어요"가 뜬다. 그 경우 데이터 쪽은 방탈출처럼 Realtime Database로 옮길 수 있지만, 로그인 없이는 짝 비밀을 지킬 수 없어서 설계를 다시 정해야 한다.

## 처음 설정

1. [Firebase 콘솔](https://console.firebase.google.com)에서 새 프로젝트를 만든다. 방탈출(`s1fa-escape`)과 데이터가 섞이지 않게 별도 프로젝트를 추천.
2. Authentication → 로그인 방법 → **이메일/비밀번호** 사용 설정(아래 "이메일 링크"는 끈 채로). 참여자는 실제 메일 주소로 가입하고, 비밀번호를 잊으면 로그인 화면의 "비밀번호를 잊었어요"로 재설정 메일을 받는다. Authentication → 템플릿에서 템플릿 언어를 한국어로 해 두면 좋다(앱도 한국어로 요청한다).
3. Authentication → 설정 → 승인된 도메인에 `계정명.github.io` 추가.
4. Firestore Database 만들기 (프로덕션 모드, 서울 `asia-northeast3` 권장).
5. 프로젝트 설정 → 내 앱 → 웹 앱 추가 → 설정값을 `src/firebase.config.js`에 붙여넣는다.
6. 보안 규칙 게시: Firestore → 규칙 탭에 `firestore.rules` 내용을 붙여넣고 게시. (터미널이 편하면 `firebase deploy --only firestore:rules`)
7. 로컬 실행
   ```
   npm install
   npm run dev
   ```
   Firebase 프로젝트 없이 화면을 점검하려면 `npm run dev:emu` (Java 21 이상 필요). 내 PC의 Firebase 에뮬레이터(로그인·Firestore)에 붙어서 뜨고, 데이터는 끄면 사라진다. 처음 실행할 때 에뮬레이터 파일을 내려받는다.
8. GitHub Pages 배포: 저장소 Settings → Pages → Source를 **GitHub Actions**로 바꾼 뒤 `main`에 push. 주소는 `https://계정명.github.io/저장소명/`.

## 운영 순서

운영 탭의 "다음 단계로" 버튼으로 진행한다. **단계는 되돌릴 수 없다**(보안 규칙으로 막혀 있음).

| 단계 | 운영진 | 참여자 |
|---|---|---|
| 0 준비 | 로그인 화면 아래 "처음 설정하는 운영자인가요?"로 운영자 계정 생성 → 명단 입력(이름,근무지) → 팀 편성 → 배정 방식 선택 후 배정 → 이름별 초대 코드 개별 전달 | 초대 코드로 가입, 캐릭터 고르기, 프로필 6문항 작성 |
| 1 미션 진행 | 주차(1~3) 올리기, 매주 금요일 "단서 2개 공개", 인증 0건인 사람 알림, 내용 없는 인증 무효 처리 | 미션 카드 고르기 → 수행 → 완료 알리기 / 받은 코드 입력 + 후기 20자 이상 |
| 2 최종 지목 | 대기 | 용의자 보드에서 최종 지목 |
| 3 투표 | "투표 카드 만들기", 카드별 운영진 평가(0~10) | 익명 카드 Top 3 투표 |
| 4 집계 | "집계하기", 베스트 후기상 선택 | 대기 |
| 5 공개 | 결과 탭에서 4등 → 3등 → 2등 → 대추첨 순서로 추첨 | 결과 확인 |

명단 입력 형식은 한 줄에 한 명, `이름,근무지` 또는 `이름,근무지,팀번호`. 근무지는 `SR3`, `S1L` (`src/lib/constants.js`의 `LOCS`에서 바꿀 수 있음). 명단 표에서 근무지를 눌러 바꿀 수도 있다.

운영자도 참여하려면 명단을 만든 뒤 운영 탭에서 자기 이름의 초대 코드로 연결한다.

## 규칙 요약 (코드에 반영된 것)

- 배정: 한 바퀴로 이어지는 원형 배정. 자기 자신·같은 팀·서로 마니또인 쌍은 생기지 않는다. 운영 화면에서 두 방식 중 고른다.
  - **근무지 상관없이(기본)**: 다른 근무지끼리도 짝이 된다. 대상이 다른 근무지면 쪽지·플레이리스트·공범 섭외처럼 직접 가지 않아도 되는 카드만 나온다.
  - **같은 근무지끼리만**: 근무지별로 원이 따로 생긴다. 3명 미만인 근무지는 큰 근무지 원에 합친다. 추리 보드에서 다른 근무지가 후보에서 빠진다.
  - 같은 팀을 피할 수 없는 그룹이 생기면 그 그룹만 팀 조건을 풀고 운영 화면에 경고를 띄운다. 이 경우 추리 보드도 팀으로 후보를 줄이지 않는다.
- 미션: 1·2주차는 쉬움·보통·도전 카드 3장 중 1장 선택, 3주차는 전원 칭찬 카드. 미션마다 4자리 인증 코드.
- 인증: 사진 없이 받는 사람이 코드 + 후기(20자 이상) 입력. 코드는 자기 마니또가 보낸 것만 통과.
- 단서: 마니또의 프로필 답변이 운영자가 공개한 개수만큼만 보인다(매주 2개, 최대 6개).
- 응모권: 미션 인증 1장(최대 3), 도전 미션 +1장(최대 2), 받는 사람 인증 입력 1장(최대 3), 끝까지 안 들킴 2장, 정답 지목 1장. 수상 제외자는 0장.
- 베스트 마니또: 완수율 30% + 전체 투표 50% + 운영진 평가 20%. 투표 카드는 사람마다 다른 순서·번호로 보이고, 자기 팀 카드는 빠진다.
- 추첨: 응모권 수에 비례. 2~4등끼리는 중복 당첨 없음, 대추첨은 전원 대상.

## 로그인과 같은 기기 사용

- 메일 주소 + 비밀번호로 로그인한다. 메일 주소는 Firebase Authentication에만 있고 Firestore에는 저장하지 않아 다른 참여자는 볼 수 없다(Firebase 콘솔의 Authentication 화면에서는 보인다). 내 프로필 화면에 로그인한 메일이 표시된다.
- 같은 기기를 여러 사람이 쓸 수 있다. 헤더에 지금 로그인한 사람이 "○○님 로그아웃"으로 보이고, 로그아웃 후 다른 사람이 자기 계정으로 로그인하면 된다. 사람이 바뀌면 화면 상태를 통째로 새로 만들어 앞 사람의 이름·데이터가 남지 않는다.
- 로그인 화면의 "이 기기에서 로그인 유지"를 해제하면 그 탭을 닫을 때 로그아웃된다(공용 기기용). 체크하면(기본) 로그아웃하기 전까지 유지된다.
- 비밀번호를 잊으면 "비밀번호를 잊었어요" → 메일의 링크에서 새 비밀번호를 정한다. 가입 메일 주소를 틀리게 적었다면 운영자가 Firebase 콘솔 Firestore의 `roster/{pid}` 문서에서 `uid`를 비우고(null), 본인이 새 메일로 가입하면서 같은 초대 코드를 넣으면 다시 연결된다. 프로필·미션·인증 기록은 이어진다.

## 무료 한도와 읽기 수

무료 요금제(Spark)는 Firestore 읽기에 하루 한도가 있다(알려진 값 5만 건, 한국 시간 오후 5시쯤 초기화). 넘으면 그날 남은 시간 동안 모두 데이터를 못 불러온다. 그래서 같은 내용을 덜 읽게 만들어 두었다(행사 규칙·화면 순서는 그대로).

- 명단: 참여자 화면은 56명 문서 대신 요약 문서 `public/roster` 1건(이름·팀·근무지)을 읽는다. 운영 탭을 열면 명단과 요약이 다를 때 자동으로 다시 쓴다(미션 시작 때도 한 번 더 씀). 운영 화면은 전체 명단을 그대로 읽는다.
- 캐릭터: 전원 것을 구독하지 않고 화면에 나온 사람 것만 읽어 두고, 10분이 지나면 다시 읽는다. 다른 사람이 캐릭터를 바꾸면 최대 10분 늦게 보인다.
- 피드: 최근 30건씩, "더 보기"로 30건 더. 답장은 화면에 나온 후기 것만 읽는다.
- 기기 저장소 캐시는 쓰지 않는다. 같은 기기를 여러 사람이 쓸 때 앞 사람 데이터가 기기에 남지 않게 하기 위해서다.

코드로 계산한 추정치(측정값 아님): 사이트 한 번 열기 약 130건 → 약 20건(내 미션 화면 기준), 피드 열기 최대 약 340건 → 약 60건. 추리 보드는 후보 캐릭터 때문에 처음 열 때 후보 수만큼 더 읽는다. 행사 중에는 Firebase 콘솔 → Firestore → 사용량에서 하루 읽기 수를 확인할 것.

## 비밀 유지 범위와 한계

- 참여자: 남의 배정·코드·단서·쪽지를 읽을 수 없다(보안 규칙).
- 운영자: 앱에서는 **투표 단계(3) 전까지 짝 정보를 읽을 수 없다**. 단계는 되돌릴 수 없어서 몰래 앞으로 갔다 돌아오는 것도 안 된다.
- 단, 다음은 막을 수 없다.
  - Firebase 콘솔에 접근할 수 있는 사람은 Firestore 데이터를 직접 볼 수 있다.
  - 배정은 운영자 브라우저에서 계산된다. 운영자도 참여한다면 배정 직후 개발자 도구를 열지 않아야 한다.
  - 개발자 도구로 Firestore에 직접 요청을 보내면 팀 현황판의 미션 수, 투표 대상(본인 카드 포함) 같은 일부 값은 조작할 수 있다. 응모권 핵심(인증 코드 검증, 단계 역행, 미션 난이도 바꾸기)은 규칙으로 막았다. 난이도는 완료 표시를 했거나 그 슬롯 코드가 이미 인증되면 바꿀 수 없고, 3주차 칭찬 슬롯에는 칭찬 카드만 들어간다.
- 재배정용 메모(`meta/assignment`)는 운영자가 언제든 읽을 수 있어서, 코드·사람 목록을 정렬해 저장한다(배정 순서가 드러나지 않게).

## 테스트

```
npm test
```
배정(56명 8팀 반복, 근무지 상관없이 모드에서 다른 근무지 짝 발생, 같은 근무지 모드에서 SR3/S1L 3~53명 모든 비율, 소수 근무지 합치기, 팀 조건 해제), 코드 중복, 재배정 메모 정렬, 응모권 계산, 정체 누설 시 합계 −1장, 가중 추첨, 최다 응모권상, 베스트 마니또 순위를 확인한다.

```
npm run test:rules
```
Firestore 에뮬레이터를 띄워 `firestore.rules`를 확인한다(Java 21 이상 필요). 두 종류다.

- 막아야 하는 것: 남의 배정·코드·단서·쪽지·프로필 읽기, 남에게 발급된 코드로 인증, 단계 역행, 운영자의 투표 단계 전 짝 정보 열람, 완료했거나 인증된 슬롯의 난이도 변경, 초대 코드 가로채기 등
- 앱이 실제로 보내는 요청이 거부되지 않는 것: 각 화면이 Firestore에 쓰는 값의 모양을 그대로 옮겨 적은 "앱 흐름" 테스트. **화면에서 쓰는 값(필드 이름·타입·길이)을 바꾸면 규칙과 이 테스트를 같이 고칠 것.**

GitHub Actions도 같은 순서(`npm test` → `npm run test:rules` → `npm run build`)로 돌린다. main은 통과해야 배포되고, 다른 브랜치는 테스트만 한다.

에뮬레이터로는 확인할 수 없는 것(실제 프로젝트에서 직접 확인할 것):

1. 규칙 게시가 오류 없이 끝나는지
2. 사내 PC·사내 와이파이 휴대폰에서 가입과 데이터 읽기·쓰기가 되는지(위 "사내망 확인")
3. 실제 Firebase 프로젝트 설정값(`src/firebase.config.js`)으로 로그인·가입이 되는지
4. 테스트 계정 2~3개로 운영자 설정 → 명단 → 배정 → 가입 → 미션 완료 → 코드 입력 → 단서 공개가 되는지 (같은 흐름을 `npm run dev:emu`로 로컬에서 먼저 볼 수 있다)

## 연말 장식

눈 내림, 전구 줄, 패널 제목의 호랑가시 잎, 로고의 산타 모자, 트리·선물, 선물 리본은 `src/xmas.jsx`, `src/xmas.css`, `src/assets/xmas/`에만 있다. 기본 색·테두리·버튼·대사창(방탈출 값)은 `styles.css`에서 바꾸지 않았다. 움직임 줄이기 설정을 켠 기기에서는 눈과 전구가 멈춰 있다.
