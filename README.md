# S1FA 마니또 사이트

부서 송년회(2026-12-09) 전 3주 동안(11/17~12/8) 진행하는 마니또 미션 사이트. 미션 배정, 인증 코드, 받는 사람 인증, 주간 단서, 용의자 보드, 최종 지목, 응모권 집계, 송년회 발표 화면과 현장 추첨까지 한 곳에서 한다.

- 프런트엔드: React 18 + Vite 5
- 호스팅: GitHub Pages (방탈출과 같음, `main`에 올리면 자동 배포)
- 백엔드: Firebase 무료 요금제(Spark) — Authentication(메일 주소/비밀번호), Firestore
- 서버 코드(Cloud Functions)는 쓰지 않는다. 비밀 유지는 전부 `firestore.rules`(보안 규칙)로 처리한다.

## 방탈출(office-escape)에서 가져온 것

| 가져온 것 | 이유 |
|---|---|
| 화면 디자인 | GBA/포켓몬 스타일 색, 테두리, 버튼, 대사창, 로고를 방탈출 `style.css` 값 그대로 따랐다. |
| 참가자 캐릭터 4종 | 방탈출 `assets/img/char/p1~p4.png`를 `public/char/`에 복사. 내 프로필에서 고르고, 내 대상·용의자 보드·결과 발표에 나온다. |
| 파트장님·PL님 캐릭터 | 방탈출 `assets/img/char/boss1~4.png`(파트장님 세 분, PL님)를 `public/char/`에 복사. 로그인 화면 주인공으로 나온다(연말에는 크리스마스 소품을 얹은 그림). |
| 근무지 구분(SR3/S1L) | 대상이 다른 근무지면 직접 가지 않아도 되는 미션 카드만 나온다. 배정은 기본이 근무지 상관없이(다른 근무지끼리도 짝), 필요하면 같은 근무지끼리만으로 바꿀 수 있다. |
| GitHub Pages 호스팅 | 사내망에서 열리는 것이 이미 확인된 방식. Firebase Hosting의 하루 전송량 한도(360MB)도 피한다. |
| 갈무리 글꼴(jsDelivr) | 방탈출과 같은 글꼴이고, jsDelivr는 사내망에서 열리는 것이 확인됐다. 본문은 기기 기본 글꼴이라 외부 다운로드가 없다. |
| Firebase 설정을 코드 파일에 두는 방식 | 방탈출 `net.js`처럼 `src/firebase.config.js`에 둔다. 공개돼도 되는 값이고 보호는 보안 규칙이 맡는다. |
| "처음 들어온 사람이 운영자" 방식 | 방탈출의 관리자 비밀번호 고정 방식과 같은 발상. 참여자에게 링크를 주기 전에 운영자가 먼저 접속해야 한다. |
| 배포 전 점검 스크립트 습관 | `npm test`가 배정·응모권·추첨을 확인하고, 배포 워크플로가 테스트를 통과해야 배포한다. |

가져오지 않은 것: 방탈출의 기기별 임시 ID 방식(로그인 없음)은 쓰지 않았다. 마니또는 누가 누구를 맡았는지 숨겨야 해서 계정 로그인(Firebase Authentication)이 필요하다. 데이터베이스도 방탈출의 Realtime Database 대신 Firestore를 쓴다.

## 사내망 확인 (배포 전 꼭)

방탈출로 사내망에서 열리는 것이 확인된 곳: `github.io`, `cdn.jsdelivr.net`, `www.gstatic.com`, `*.firebasedatabase.app`.

이 사이트는 여기에 더해 아래 곳을 쓴다. **사내 PC와 사내 와이파이 휴대폰에서 각각 가입 한 번 해 보고** 되는지 확인할 것.

- `identitytoolkit.googleapis.com`, `securetoken.googleapis.com` (로그인)
- `firestore.googleapis.com` (데이터)
- `프로젝트ID.firebaseapp.com` (비밀번호 재설정 메일의 링크가 여는 페이지)

비밀번호 찾기도 한 번 해 볼 것. 재설정 메일은 `noreply@프로젝트ID.firebaseapp.com`에서 오는데, 회사 메일이면 차단되거나 스팸함으로 갈 수 있다. 사내망에서 링크가 안 열리면 휴대폰 데이터로 열어도 된다.

막혀 있으면 가입 화면에 "로그인 서버에 연결하지 못했어요"가 뜬다. 그 경우 데이터 쪽은 방탈출처럼 Realtime Database로 옮길 수 있지만, 로그인 없이는 짝 비밀을 지킬 수 없어서 설계를 다시 정해야 한다.

사내에서 생길 수 있는 문제와 대처(확인한 근거가 있는 것만):

| 증상 | 원인 후보 | 대처 |
|---|---|---|
| 로그인은 되는데 **1시간쯤 지나면** 저장·불러오기가 안 됨 | 로그인 유지 토큰을 1시간마다 `securetoken.googleapis.com`에서 새로 받는데, 그 주소만 막힌 경우 | 위 주소를 사내 PC에서 같이 확인. 막혀 있으면 휴대폰 데이터로 사용 |
| 화면이 "불러오는 중"에서 멈추거나 실시간 갱신이 안 됨 | 사내 프록시가 Firestore의 실시간 연결(스트리밍)을 끊거나 묶어 둠. SDK가 자동으로 긴 폴링으로 바꾸지만 감지가 실패할 수 있음 | 사이트 주소 끝에 `?longpoll`을 붙여 한 번 열면 그 기기에서는 계속 긴 폴링으로 연결한다(`?longpoll=0`으로 되돌림, `src/firebase.js`) |
| 가입 중 "잠시 후 다시" 류의 오류가 몰려서 남 | Firebase는 **같은 IP에서 새 계정을 시간당 100개까지** 만든다(공식 제한). 사내 PC는 대부분 같은 외부 IP로 나간다 | 54명이 한 시간 안에 가입해도 100개보다 적지만, 시험 계정까지 한꺼번에 만들지 말 것. 막히면 1시간 뒤 다시 |
| 비밀번호 재설정 메일이 안 옴 | 회사 메일이 `noreply@프로젝트ID.firebaseapp.com`을 막거나 스팸함으로 보냄 | 스팸함 확인. 안 되면 운영자가 "연결 해제" 후 새 초대 코드로 다시 가입(기록은 이어짐) |
| App Check를 켠 뒤 사내에서만 사이트가 멈춤 | reCAPTCHA(`www.google.com`)가 사내망에서 막힘 | App Check "적용"을 끈다(바로 돌아옴). 아래 "App Check (선택)" |

## 처음 설정

1. [Firebase 콘솔](https://console.firebase.google.com)에서 새 프로젝트를 만든다. 방탈출(`s1fa-escape`)과 데이터가 섞이지 않게 별도 프로젝트를 추천.
2. Authentication → 로그인 방법 → **이메일/비밀번호** 사용 설정(아래 "이메일 링크"는 끈 채로). 참여자는 실제 메일 주소로 가입하고, 비밀번호를 잊으면 로그인 화면의 "비밀번호를 잊었어요"로 재설정 메일을 받는다. Authentication → 템플릿에서 템플릿 언어를 한국어로 해 두면 좋다(앱도 한국어로 요청한다).
3. Authentication → 설정 → 승인된 도메인에 `계정명.github.io` 추가.
4. Firestore Database 만들기 (프로덕션 모드, 서울 `asia-northeast3` 권장).
5. 프로젝트 설정 → 내 앱 → 웹 앱 추가 → 설정값을 `src/firebase.config.js`에 붙여넣는다.
6. 보안 규칙 게시: Firestore → 규칙 탭에 `firestore.rules` 내용을 붙여넣고 게시. (터미널이 편하면 `firebase deploy --only firestore:rules`)
   **`firestore.rules`가 바뀔 때마다 다시 게시해야 한다.** 게시를 잊으면 운영 화면 맨 위에 "게시된 보안 규칙이 지금 사이트와 맞지 않아요" 경고가 뜬다(규칙의 `rulesVersion`과 `src/lib/constants.js`의 `RULES_VERSION`을 맞춰 보는 방식).
7. 로컬 실행
   ```
   npm install
   npm run dev
   ```
   Firebase 프로젝트 없이 화면을 점검하려면 `npm run dev:emu` (Java 21 이상 필요). 내 PC의 Firebase 에뮬레이터(로그인·Firestore)에 붙어서 뜨고, 데이터는 끄면 사라진다. 처음 실행할 때 에뮬레이터 파일을 내려받는다.
8. GitHub Pages 배포: 저장소 Settings → Pages → Source를 **GitHub Actions**로 바꾼 뒤 `main`에 push. 주소는 `https://계정명.github.io/저장소명/`.
9. 인증 메일: Authentication → 템플릿에서 "이메일 주소 인증"과 "비밀번호 재설정"의 언어를 한국어로 바꾸고 보낸 사람 이름을 정한다(보낸 사람 주소는 `noreply@프로젝트ID.firebaseapp.com`). 사이트 주소를 Firebase Hosting으로 옮겼다면 Authentication → 설정 → 승인된 도메인에 그 주소가 있는지 확인한다(`프로젝트ID.web.app`은 기본으로 들어 있다).
10. (선택) 짧은 주소: 아래 "짧은 주소(Firebase Hosting)".
11. (선택) App Check: 아래 "App Check (선택)"를 볼 것. 켜지 않아도 사이트는 동작한다.

## 가입 방식 (회사 메일 인증 + 초대 코드 예비)

1. 운영자가 명단에 `이름, 파트, 아이디`를 넣는다. 아이디 뒤에 `@samsung.com`(`MAIL_DOMAIN`)이 붙어 그 사람의 메일이 된다(`roster.email`, 그리고 메일 → 명단 번호를 찾는 `mailIndex/{메일}`).
2. 운영 탭 "가입 안내 메일"에서 명단의 아이디로 가입 링크(`주소?join`, 열면 "처음 가입" 화면)를 보낸다. 운영자의 회사 메일에서 보낸다(사이트가 직접 보내지 못한다): "메일 앱으로 열기"를 누르거나 주소·제목·본문을 복사해 새 메일에 붙여 넣는다. 참여자는 숨은 참조(BCC)에.
3. 참여자는 "처음 가입"에서 **아이디와 새 비밀번호**만 넣는다. 가입하면 그 메일로 인증 메일이 간다(Firebase Authentication).
4. 메일의 링크를 누르고 사이트로 돌아오면(또는 "인증했어요 · 연결하기"를 누르면) 명단의 자기 이름과 연결된다. 보안 규칙이 "인증을 마친 메일이 명단의 그 사람 메일과 같은지"를 확인하므로, 남의 아이디로 가입해도 그 사람의 메일함을 열 수 없으면 연결되지 않는다.
5. **인증 메일이 오지 않거나 링크가 열리지 않는 사람**은 운영자가 초대 코드를 알려 주면 "연결 전" 화면(또는 가입 화면의 "초대 코드" 칸)에 넣어 연결한다. 초대 코드는 명단을 넣을 때 전원에게 만들어져 있다(운영 탭 명단 표, "초대 코드·메일 보기").

확인할 것: 회사 메일이 `noreply@프로젝트ID.firebaseapp.com`의 메일을 받는지, 메일 속 링크(`프로젝트ID.firebaseapp.com`)가 사내망에서 열리는지. 배포된 사이트의 "비밀번호를 잊었어요"로 먼저 시험할 수 있다(보낸 사람과 링크 주소가 인증 메일과 같다). 사이트 비밀번호는 회사 비밀번호와 다르게 정하라고 안내할 것.

운영자 계정을 다른 메일로 바꾸려면: 새 메일로 `?setup` 주소에서 "운영자·공동 운영자 계정 만들기" → "연결 전" 화면의 계정 번호를 복사 → 예전 운영자 계정으로 운영 탭 "공동 운영자"에 그 번호를 추가 → Firebase 콘솔 → Firestore → `config/app` → `admins` 배열에서 **새 계정 번호를 맨 위(0번)로** 옮기고 예전 번호를 지운다(처음 운영자는 0번 계정이다) → Authentication에서 예전 계정을 삭제.

## 짧은 주소 (Firebase Hosting)

`https://계정명.github.io/저장소명/` 대신 `https://프로젝트ID.web.app`(지금 프로젝트는 `https://s1fa-manito.web.app`)으로 열 수 있다. 무료(Spark)이고 같은 빌드를 그대로 올린다(`firebase.json`의 `hosting`). 두 주소는 같은 Firebase 프로젝트(같은 계정·같은 데이터)를 쓴다.

- 자동 배포(권장): Firebase 콘솔 → Hosting → "시작하기"로 켠다 → 프로젝트 설정 → 서비스 계정 → "새 비공개 키 생성"으로 받은 JSON 파일의 내용을 GitHub 저장소 Settings → Secrets and variables → Actions → New repository secret에 이름 `FIREBASE_SERVICE_ACCOUNT`로 넣는다(파일은 넣은 뒤 지운다. 이 키는 프로젝트 전체 권한이라 다른 곳에 올리지 말 것). 그다음부터 `main`에 올릴 때마다 GitHub Pages와 Firebase Hosting에 같이 배포된다(`.github/workflows/deploy.yml`). 비밀값이 없으면 그 단계는 건너뛴다.
- 한 번만 직접 올리기: 내 PC에서 `npm ci && npm run build && npx firebase login && npx firebase deploy --only hosting --project 프로젝트ID`. 이후 코드가 바뀌면 다시 올려야 한다(안 올리면 두 주소의 버전이 달라진다).
- 주소를 옮긴 뒤에는 참여자에게 새 주소만 알린다. 로그인 유지·"안 읽은 표시"는 주소(도메인)마다 따로 기억된다.

## 운영 순서

운영 탭의 "다음 단계로" 버튼으로 진행한다. **단계는 되돌릴 수 없다**(보안 규칙으로 막혀 있음).

**가입과 배정은 서로 기다리지 않는다.** 배정은 명단에 있는 사람 전원으로 하고(가입 여부와 무관), 가입은 미션이 시작된 뒤에도 언제든 할 수 있다. 권장 순서: ① 명단 입력(엑셀에서 `이름·파트·아이디` 세 칸을 복사해 그대로 붙여 넣는다) → ② 사이트 주소 공지, 가입 기간 하루(11/17) → ③ 11/18 아침에 가입 현황을 보고(운영 탭 "2. 마니또 배정"에 가입 안 한 사람 이름이 나온다) 안 한 사람에게 직접 연락, 참여하지 않겠다는 사람은 명단에서 삭제 → ④ **"배정하기" → "다음 단계로: 미션 진행"을 이어서** 누른다. 배정하는 순간 가입한 사람에게 자기 대상이 보이므로 배정은 미션을 시작하는 날에 한다. 가입 안 한 사람도 배정된 채로 두고(가입 전까지 불참 처리: 그 사람의 마니또가 한 미션은 자동 인정, 그 사람의 대상에게는 2주차부터 수호천사가 연결되고 못 받은 주차 보상이 붙는다), 나중에 가입하면 그때부터 그대로 참여한다.

| 단계 | 운영진 | 참여자 |
|---|---|---|
| 0 준비 | 사이트 주소 끝에 `?setup`을 붙여 들어가 "운영자·공동 운영자 계정 만들기"로 운영자 계정 생성 → 명단 입력(이름, 파트, 아이디) → 가입 기간 → 미션을 시작하는 날 "배정하기"("짝 현황 보기"로 결과 확인) → 인증 메일이 안 오는 사람에게만 초대 코드를 개별 전달(얼굴 보고 또는 1:1 메시지) | 회사 메일 아이디로 가입 → 회사 메일로 온 인증 링크 누르기 → 명단의 내 이름과 자동 연결 → 캐릭터·프로필 6문항·"내 마니또에게 알려 줄 것" 작성 |
| 1 미션 진행 | 주차(1~3) 올리기, 매주 금요일 "단서 2개 공개"(주차마다 2개까지, 파트 순위도 같이 발표됨), 공지로 마감 안내, "짝 현황" 표로 주차별 진행 챙기기, 인증 0건인 사람 알림, "받은 게 없어요" 신고를 주차별로 확인(받았음·못 받음), 내용 없는 인증 무효 처리, 신고된 쪽지 검토, 더 참여 못 하는 사람은 "중도 이탈" 표시 | 미션 카드 고르기 → 수행 → 완료 알리기(완료한 주차에는 "쪽지 더 보내기") / 받은 코드 입력 + 받은 것이 마니또가 고른 카드와 맞는지 확인 + 후기 20자 이상 / 받은 게 없으면 "받은 게 없어요" / 불쾌한 쪽지는 "이 쪽지 신고" |
| 2 최종 지목 | 운영 탭에서 지목 안 한 사람 확인("짝 현황" 표에 누구를 지목했는지와 정답 여부가 나온다). 지목을 안 하면 그 사람의 마니또가(미션 3건이 모두 인정됐다면) 은신 2장을 받으니 마감 전에 알릴 것 | 용의자 보드에서 최종 지목 |
| 3 마감 | 지목이 끝나고 집계를 기다리는 단계(예전의 투표 단계. 투표는 없앴고 단계는 한 칸씩만 넘어가서 번호는 남겼다). 수상 제외·중도 이탈 표시와 "받은 게 없어요" 확인을 마무리 | 대기 |
| 4 집계 | **3주차 "황금 카드 추첨"을 먼저 끝낸다**(추첨하지 않은 주차의 커피 쿠폰 당첨자는 발표 화면에 안 나온다. 집계 패널이 알려 준다) → "집계 전 확인" 표 처리(완료를 알렸는데 인증이 없는 주차를 두 사람에게 확인하고 주차별로 "받았음" 또는 "못 받음") → 수상 제외·중도 이탈 표시 마무리 → "집계하기" → "검산"(저장된 응모권 표를 지금 자료로 다시 계산해 비교). 3등 베스트 후기상은 집계할 때 공감 수로 정해진다(운영자가 고르지 않는다). **집계해야 공개 단계로 넘어갈 수 있다** | 대기 |
| 5 공개 | 결과 탭 "발표 화면 열기"로 큰 화면에 띄우고 장면을 넘긴다(아래 "송년회 발표 화면"). 시상은 발표 화면에서: **현장에서 정한 숫자 하나**를 넣으면 2등·3등이 정해지고, 4·5등과 1등은 통에서 종이를 뽑아 이름을 입력하고, 6등은 사이트가 뽑는다. 6등을 뽑은 뒤에는 수상자를 바꿀 수 없다 | 결과 탭에서 내 마니또·내 응모권·수상자 확인(무대에서 넘긴 장면까지만 보임), 6등은 휴대폰으로 확인 |

명단 입력 형식은 한 줄에 한 명, `이름, 파트, 아이디`(쉼표 또는 탭. 엑셀에서 세 칸을 복사해 붙여 넣으면 탭이다). **아이디는 회사 메일의 @ 앞부분**이고 `src/lib/constants.js`의 `MAIL_DOMAIN`(지금 `samsung.com`)이 뒤에 붙는다. 아이디를 비우면 그 사람은 초대 코드로만 가입한다. 명단 표에서 파트·아이디를 눌러 고칠 수 있다(아이디는 처음 운영자만). 근무지는 더 이상 입력하지 않는다(예전에 근무지를 넣어 둔 명단은 그대로 동작하고, 그때만 "같은 근무지끼리만" 배정 옵션이 보인다). "파트"는 실제 소속 파트이고, **같은 파트끼리는 마니또가 되지 않게** 배정하며 파트 순위와 마지막 단서(마니또의 파트)에 쓴다.

참여 인원은 54명(부서 56명 중 운영자와 PL님 제외)을 기준으로 했다. 인원 수는 코드에 고정돼 있지 않고 명단에 넣은 사람 수대로 동작한다.

### 송년회 발표 화면

결과 탭(공개 단계, 운영자) → "발표 화면 열기". 큰 화면(노트북 + 프로젝터)에 띄우고 →·Space(다음), ←(이전), F(전체 화면)로 넘긴다. 닫기는 "닫기" 버튼으로만 한다(닫으면 운영자 결과 탭에 모든 결과가 보여서, 추첨 뒤 발표 중에는 한 번 묻는다). 참여자 휴대폰에는 무대보다 조금 늦게(약 2초, 추첨 발표는 이름이 다 돌아간 뒤에) 열린다.

1. 오프닝: 참여 인원, 인증된 미션 수, 추가 쪽지·후기·공감·"마니또에게 한마디" 수
2. 파트 대항전 최종 순위 → "우승 파트는…" (파트원 +1장)
3. **정체 공개(짝마다 두 장)**: "○○님의 마니또는…?"(그 사람이 지목한 사람 표시) → 정답 공개(맞혔는지, "몇 주차부터 알고 있었어요", 마니또가 한 미션 목록). 공개된 마니또가 다음 차례의 주인공이 되도록 원을 따라 이어진다. "자동 넘기기"(질문 3초·정답 5초)와 "남은 짝 건너뛰기"가 있다
4. 명탐정: 정답 지목 인원, "가장 먼저 알아챈 사람"(주차별 추측을 일찍부터 끝까지 맞힌 사람) → 숨은 수호천사(있을 때)
5. 칭찬 벽(3주차 칭찬 카드가 흘러감. 카드 수에 맞춰 마지막 카드까지 흘러간다)
   → **송년회 칭호**(받은 사람이 있는 칭호만 한 장면씩. 응모권·상품과 무관하고 집계할 때 기록으로 자동으로 정해진다. 1등이 여럿이면 모두):
   🏆 도전왕(대상이 인증하고 "카드와 같아요"를 확인한 도전 미션(황금 카드 포함)이 가장 많은 마니또), ✨ 황금손(황금 카드 미션을 그렇게 인증받은 마니또 모두, 커피 쿠폰 당첨과 별개),
   💌 쪽지 장인(내 대상에게 보낸 쪽지 — 완료 알림·칭찬 카드·쪽지 더 보내기, 빈 쪽지·가린 쪽지 제외 — 가 가장 많은 마니또),
   🫥 투명 마니또(은신 응모권을 받았고(내 미션 3건 + 단서 6칸) 대상이 주차별 추측에서도 한 번도 고르지 않은 마니또. 대상이 가입 안 함·중도 이탈이면 제외)
   → **☕ 황금 카드 5천원 커피 쿠폰 당첨자**(2주차·3주차를 나란히. 운영 화면 "황금 카드 추첨"의 기록을 집계할 때 옮겨 둔 것)
6. **시상 시작**: 참석자에게 숫자 하나를 받아 넣고 "숫자 정하기" → 한 번 더 눌러 확정(한 번 정하면 바꿀 수 없다. 정하기 전에는 다음 장면으로 넘어가지 않는다). 이 숫자는 2등 동점을 가르고 6등 사이트 추첨에 쓴다
7. **2등 베스트 마니또** 3명(한 명씩) → **3등 베스트 후기상**(2등 수상자를 뺀 공감 1위 후기). 사이트가 정한다
8. **4등 → 5등(종이 추첨)**: 통에서 이름 종이를 뽑아 읽고, 화면의 입력 칸에 이름 일부를 치면 후보가 나와 누르면 들어간다. 이미 상을 받은 사람이나 응모권 0장인 사람은 들어가지 않는다(다시 뽑는다). 잘못 넣은 이름은 옆의 ✕로 지운다. 입력한 이름은 참여자 휴대폰에도 바로 보인다
9. **1등 대추첨(종이)**: 이미 2~5등인 사람이 뽑혀도 1등이다. 그 사람은 1등만 받는다
10. **겹친 자리 다시 채우기**: 1등이 받았던 자리를 채운다. 2등은 다음 순위, 3등은 다음으로 공감이 많은 후기가 자동으로 올라오고, 4·5등은 종이를 더 뽑아 입력한다. 2·3등으로 올라간 사람이 4·5등이었다면 더 큰 상을 받고 그 자리도 다시 뽑는다(응모권이 더 많은 사람이 더 작은 상에 머물지 않게)
11. **6등(사이트 추첨)**: "6등 추첨하기" → 한 번 더 눌러 확정. 1~5등을 받은 사람을 빼고 숫자와 응모권 표로 뽑는다. 각자 휴대폰 결과 탭에서 "축하해요! ○○님은 6등…" 또는 "이번에는 뽑히지 않았어요"를 본다. **뽑은 뒤에는 1~6등을 모두 바꿀 수 없다**
12. 마무리

종이 추첨 준비: 집계 단계의 "집계" 패널에 "이름 종이 N장 보기" → "인쇄"가 있다. 사람마다 응모권 수만큼 이름 종이가 나오니 잘라서 각자 접어 통에 넣게 한다(마지막 집계 뒤에 인쇄할 것). 저장되는 값은 숫자, 종이로 뽑힌 이름(1·4·5등), 6등뿐이고 2·3등과 겹친 자리 정리는 그 값들로 계산한다(`scoring.js` `resolvePrizes`).

사람이 많아도 한 장에 들어가게 했다(1280×720·1024×768·1920×1080에서 확인): 명탐정은 인원이 늘수록 캐릭터가 작아지다 33명부터 이름만, 숨은 수호천사는 9쌍부터 한 줄씩, 6등 20명은 작은 캐릭터로. 칭호(14명)·커피 쿠폰(2주 10명)은 1280×720에서 확인(`awards.cjs`). 그래도 넘치는 화면에서는 무대가 위에서부터 스크롤된다.

넘긴 장면 번호가 결과 문서(`results/public.step`)에 남고, 참여자 휴대폰의 결과 탭은 **그 장면까지만** 열린다(내 마니또는 내 짝 장면이 지나야 보인다). 발표 없이 끝내려면 "발표 없이 모두 공개". 54쌍을 한 쌍씩 공개하면 약 108장이라, 시간이 부족하면 중간에 "자동 넘기기"나 "남은 짝 건너뛰기"를 쓴다.

## 운영자와 공동 운영자

운영자와 공동 운영자는 **마니또에 참여하지 않는 계정**이다. 명단에 넣지 않고, 초대 코드로 명단에 연결할 수도 없다(보안 규칙이 막는다). 반대로 명단에 연결된 계정(참여자)은 운영자가 될 수 없다. 참여하지 않기 때문에 누가 누구의 마니또인지, 주차별 진행, 쪽지 내용, 마니또가 낸 단서, 최종 지목을 처음부터 볼 수 있다(운영 탭 "짝 현황").

**처음 운영자(운영자 목록의 첫 번째 계정)만 할 수 있는 것**: 공동 운영자 지정·해제와 메모 수정, 명단 추가·삭제와 아이디(메일) 고치기, 초대 코드 발급·새로 만들기·보기 목록, 계정 연결 해제, "못 받음" 확정·취소(모두 보안 규칙이 막는다). 공동 운영자는 그 밖의 운영(단계·주차·단서·배정·짝 현황·확인·무효 처리·집계·추첨)을 한다. 공동 운영자 계정 하나를 빼앗겨도 운영자를 늘리거나 남의 계정을 명단에 연결할 수 없게 하려는 것이다(보안 규칙). 그래서 처음 운영자 계정의 비밀번호는 특히 길고 다른 곳에 쓰지 않는 것으로 정한다. 처음 운영자를 바꾸는 기능은 없다.

공동 운영자 지정 방법:

1. 지정할 사람이 사이트 주소 끝에 `?setup`을 붙여 들어가 "운영자·공동 운영자 계정 만들기"로 계정을 만든다(이미 계정이 있으면 로그인만 하면 된다. 단, 참여자로 연결된 계정은 안 된다).
2. 이미 운영자가 있으므로 그 계정은 "연결 전" 화면으로 가고, 거기에 **계정 번호**가 나온다. 초대 코드는 입력하지 않는다. **계정 번호는 그 사람의 화면을 직접 보고 받는다**(메신저로 받은 번호는 다른 사람이 끼워 넣은 것일 수 있다).
3. 처음 운영자가 운영 탭 맨 아래 "공동 운영자"에 계정 번호와 메모(누구 계정인지)를 넣고 지정한다. 지정된 사람이 "지정됐는지 다시 확인"을 누르면(또는 탭을 다시 열면) 운영 화면으로 바뀐다.

권한을 빼면 그 계정은 다시 "연결 전" 화면으로 돌아간다. 예전 방식(참여자를 공동 운영자로 지정)으로 남아 있는 계정이 있으면 "공동 운영자" 패널에 경고가 뜨니 권한을 빼고 별도 계정을 지정한다.

## 규칙 요약 (코드에 반영된 것)

- 배정: 한 바퀴로 이어지는 원형 배정. 자기 자신·같은 파트·서로 마니또인 쌍은 생기지 않는다. 운영 화면에서 두 방식 중 고른다.
  - **근무지 상관없이(기본)**: 다른 근무지끼리도 짝이 된다. 대상이 다른 근무지면 쪽지·플레이리스트·공범 섭외처럼 직접 가지 않아도 되는 카드만 나온다(명단에 근무지를 넣지 않으면 모든 카드가 나온다).
  - **같은 근무지끼리만**: 근무지별로 원이 따로 생긴다. 3명 미만인 근무지는 큰 근무지 원에 합친다. 추리 보드에서 다른 근무지가 후보에서 빠진다.
  - 같은 파트를 완전히 피하려면 (근무지 모드에서는 근무지마다) 가장 큰 파트가 인원의 절반 이하여야 한다. 넘으면 같은 파트 짝을 되도록 적게 만들고 운영 화면에 경고를 띄운다. 이 경우 `config.partExcluded = false`가 된다(운영 화면 배정 점검이 본다). 추리 보드는 11/26부터 어느 경우에도 내 파트를 후보에서 빼지 않는다(참여자 규칙에서도 같은 파트 제외를 지웠다 — "중도 이탈 처리" 참고).
  - 만드는 방법: 무작위로 섞어 맞을 때까지 반복하는 방식은 파트처럼 큰 묶음에서는 사실상 성공하지 못해서(18명 × 3파트 기준 20만 번 중 0번), 조건에 맞는 원을 먼저 만든 뒤 조건을 깨지 않는 자리 맞바꾸기로 섞는다(`src/lib/assign.js`).
  - 추리 보드는 처음부터 내 파트 사람을 후보에서 뺀다. 파트가 둘뿐이면 마지막 파트 단서는 새 정보가 되지 않는다(처음부터 다른 파트로 정해져 있음).
- 미션: 1·2주차는 난이도(쉬움·보통·도전)를 고르면 그 난이도의 카드 2장이 나오고 그중 1장을 고른다(사람·주차마다 다른 카드, 다시 뽑기 없음, 보통·도전은 돈이 드는 카드 1장 + 안 드는 카드 1장, 다른 주차에 고른 카드는 안 나옴). 3주차는 전원 칭찬 한 줄을 보내고, 원하면 보통·도전 카드를 하나 더 골라 함께 한다(카드 추가분은 1·2주차와 같은 조건). 미션마다 4자리 인증 코드. 카드 고르기·완료 알리기·인증은 **열린 주차까지만** 된다(화면뿐 아니라 보안 규칙도 막는다). 지난 주차는 미션 진행 기간 안이면 늦게라도 할 수 있다.
- 쪽지 더 보내기: 완료를 알린 주차에는 쪽지를 더 보낼 수 있다(주차마다 5건까지, `EXTRA_NOTES_MAX`). 보낸 수를 미션 문서에 같이 올리고 쪽지 문서 ID가 `{받는사람}_{주차}_n{번째}`로 정해져 있어서, 직접 요청으로도 5건을 넘길 수 없다(보안 규칙). "3일 연속 매일 다른 응원 쪽지" 카드는 첫날 완료를 알린 뒤 이것으로 이어서 보낸다. 완료 표시와 응모권에는 영향이 없다. "대상 이름 삼행시 쪽지 보내기" 카드는 도전에서 보통으로 옮겼다.
- 쪽지 신고: 받는 사람은 불쾌한 쪽지를 "이 쪽지 신고"로 알릴 수 있다(`noteFlags`). 운영 화면 "쪽지 검토"에 신고된 것이 먼저 나오고, 운영자는 가리기(받는 사람 화면에 "운영진이 가린 쪽지예요."), 추가 쪽지 삭제, 신고 처리 완료를 할 수 있다.
- 2주차 새 카드와 황금 카드: 2주차부터 쉬움·보통 카드 두 장 중 한 장은 새 카드(NEW: 밸런스 게임, 방탈출 쪽지, 비밀 지령, 실황 중계)이고 1주차에 나오던 카드는 그대로다. 2·3주차에는 난이도 칸 옆에 "✨ 황금 카드" 칸이 있어 누르면 황금 카드 두 장(돈 드는 것 + 안 드는 것: 타임어택 배달·마니또 카페, 다른 근무지 대상이면 공범 카페)이 나온다. 응모권은 도전과 같고, 그 주가 끝나면 황금 카드를 하고 대상이 "카드와 같아요"로 인증한 마니또 중 5명을 운영 화면 "황금 카드 추첨"에서 같은 확률로 뽑아 5천원 커피 쿠폰(송년회에서 발표하며 전달)을 준다. 2주차 당첨자는 3주차에서 빠지고, 5명보다 적으면 모두 당첨·남은 자리는 다음 주로. 뽑힌 마니또만 자기 내 미션 화면에서 확인한다(`goldWins/{pid}`, 본인과 운영자만 읽음). 추첨이 끝난 뒤 사이트에 들어오면, 그 주 황금 카드를 한 사람에게 결과 팝업이 뜬다(당첨은 축하, 미당첨은 위로. 주차마다 한 번, 기기마다 기억). 당첨자 이름은 송년회 전까지 알리지 않는다(황금 카드를 받은 대상이 마니또를 좁힐 수 있다). 송년회 발표 화면에는 칭호 다음에 "☕ 커피 쿠폰 당첨" 장면으로 나온다(집계 전에 3주차 추첨까지 끝낼 것).
- 송년회 칭호(응모권과 무관): 🏆 도전왕·✨ 황금손·💌 쪽지 장인·🫥 투명 마니또. 집계할 때 기록으로 정해 발표 화면에 칭호마다 한 장면씩(받은 사람이 있는 것만) 나온다. 기준은 위 "송년회 발표 화면"과 `src/lib/titles.js`.
- 미션 비용: 간식·음료·선물처럼 본인 돈이 드는 카드는 "소액 비용"으로 표시하고 건당 5천원 이하를 권장한다(`SPEND_GUIDE_WON`). 모든 난이도에 돈이 안 드는 카드가 있다. **비용 카드 미션이 대상의 인증과 카드 확인까지 받으면 응모권 +1장, 한 사람에 한 번만**(`costBonus`. 여러 번 해도, 비싼 것을 해도 1장. 돈 쓰는 것도 정성이지만 지출 경쟁이 되지 않게).
- 완료 알림: 마니또가 "미션 완료 알리기"를 누르면 완료 표시와 받는 사람에게 가는 알림(`deliveries/{받는사람}_{주차}`, 고른 카드 내용 포함)이 한 묶음으로 저장된다. 문서 ID가 정해져 있어서 한 주차에 한 번만 보낼 수 있고, 알림 없이 완료 표시만 하거나 다른 카드 내용으로 알릴 수 없다(보안 규칙).
- 인증: 사진 없이 받는 사람이 코드 + 후기(20자 이상) 입력. 코드는 자기 마니또가 보낸 것만 통과. 코드를 넣으면 그 주차에 마니또가 고른 카드가 보이고, 받은 것이 그 카드와 다르면 체크를 풀고 인증한다("카드와 다름": 보통·도전 카드의 추가 응모권이 없다. 미션 응모권 1장은 그대로). 인증하면 인증 문서(`redemptions`)와 익명 피드 글(`feed`)이 한 묶음으로 만들어진다. 운영자는 "인증 검토"에서 "카드와 다름"·"카드 확인 전"을 같음으로 고칠 수 있다.
  - **나중 카드 확인**: 마니또가 "미션 완료 알리기"를 누르기 전에 받는 사람이 메모의 코드로 먼저 인증하면, 카드를 못 보고 인증한 것이라 카드 추가분이 바로 붙지 않는다. 알림이 온 뒤 받는 사람의 "이번 주 할 일"과 추리 보드 "내가 인증한 것"에 그 카드가 나오고, "카드와 같았어요 / 달랐어요"를 한 번 고른다(보통·도전 카드만). 마니또의 "내 응모권"에는 "카드 확인 대기"로 보인다. 그래서 마니또는 미션을 하면 바로 완료 알리기를 누르는 것이 좋다(화면과 규칙 탭이 안내한다).
  - 인증은 미션 진행과 최종 지목 단계에 할 수 있다(미션 마감 직전에 온 미션을 인증할 시간). 지목이 마감되면 닫힌다.
- 익명 피드: `feed` 문서에는 받는 사람 정보도 코드도 없다(주차·후기·무효 여부·시각·감사 답장만, 문서 ID는 무작위). 인증 문서는 인증한 받는 사람, 그 코드를 가진 마니또, 운영자만 읽는다. 감사 답장은 글쓴이(받는 사람)가 자기 피드 글에 붙이고(내 인증 문서가 가리키는 글이고 후기가 같아야 함), 마니또는 자기 미션의 피드 글에서 읽는다. 글쓴이는 후기·감사 답장을 **집계 전까지 합쳐서 3번 고칠 수 있다**(추리 보드 "내가 인증한 것". 인증 문서와 피드 글을 한 묶음으로 같은 글로, 피드에 "(고침)" 표시, 공감 수는 그대로). 운영자가 가린 글을 고치면 피드 글은 빈 후기 그대로 두고 운영자만 읽는 원문 자리(`hiddenFeed`)를 고쳐서, "피드에 다시 보이기"를 누르면 고친 글이 보인다(실수로 이름을 쓴 글: 가리기 → 고쳐 달라고 하기 → 다시 보이기). 운영자는 피드 글을 가리거나 감사 답장을 지울 수 있다(운영 탭 "인증 검토"). 가리면 피드 글의 후기가 빈 값이 되고 원문은 운영자만 읽는 `hiddenFeed`로 옮겨져서, 직접 요청으로도 내용을 읽을 수 없다(보안 규칙이 원문을 옮겼는지 확인). "피드에 다시 보이기"는 그 원문으로만 되돌린다. 가린 글에는 감사 답장을 붙이거나 고칠 수 없다. 운영자가 감사 답장을 지우면 글쓴이는 새로 다시 쓸 수 있다(못 쓰게 하려면 가리기). 가리기·답장 지우기·무효 처리를 누르면 이유를 묻고(비워도 됨), 이유는 `modNotes`에 남아 **글쓴이에게만**(운영자 포함, 그 미션의 마니또는 못 봄) 추리 보드 "내가 인증한 것"과 맨 위 할 일 줄("이유 보기")로 보인다. 가리거나 무효 처리하면 글쓴이의 고칠 횟수가 다시 3번이 된다.
- 받은 게 없어요: 마니또가 완료를 알렸는데 받은 것이 없으면 받는 사람이 추리 보드에서 주차별로 알린다(1·2주차, 집계 전까지. 취소하면 문서는 남고 `active = false`가 된다). 마니또 화면에도 알림이 뜬다. 운영자가 두 사람에게 확인하고 주차마다 **받았음**(마니또의 미션으로 인정) 또는 **못 받음**(인정하지 않고 받는 사람에게 그 주차 보상)으로 정한다. 신고가 없어도 집계 단계의 "집계 전 확인" 표에서 같은 확인을 할 수 있다(받고도 인증하지 않은 경우).
- 단서 문항: 6문항 중 3개는 고르기(주로 마시는 음료, 점심, 출근 시간 — 동료가 실제로 관찰할 수 있는 것), 3개는 직접 쓰기(내 책상에 늘 있는 물건, 나만 아는 의외의 TMI, 요즘 빠져 있는 것. 2자 이상). TMI는 3주차에 공개된다. 대충 쓰거나 한 글자로 넘길 수 없다. 고르기 문항은 보기에 있는 답만 저장된다(보안 규칙이 보기 목록을 갖고 있다). 문항·보기는 `src/lib/constants.js`의 `PROFILE_QUESTIONS`에서 바꾼다(행사 시작 전에만. **바꾸면 `firestore.rules`의 보기 목록도 같이 고칠 것** — `npm test`가 둘이 같은지 확인한다).
- 단서 확인: 운영자는 "짝 현황" → "마니또가 낸 단서 보기"로 각 마니또가 대상에게 낸 단서 6칸을 본다. 거짓 단서(다른 사람인 척)는 사이트가 가려낼 수 없으니, 의심되면 운영자가 본인에게 확인한다.
- 파트 단서: 최종 지목 단계가 열리면 "내 마니또의 파트"가 마지막 단서로 공개되고, 용의자 보드가 그 파트 사람으로 좁혀진다. 배정할 때 명단의 파트로 자동으로 만들어져서 거짓으로 바꿀 수 없고, 마니또가 접속을 안 해도 나간다. 인원이 적은 파트는 이 단서만으로 거의 드러난다(운영 화면이 파트별 인원을 보여 준다).
- 단서: 마니또의 프로필 답변이 운영자가 공개한 개수만큼만 보인다(매주 2개, 최대 6개). **주차마다 2개까지만** 공개된다(공개 개수 ≤ 2 × 주차. 같은 주에 두 번 누르는 실수를 화면과 보안 규칙이 막는다). 이미 공개된 단서 칸은 프로필에서 고칠 수 없다(대상이 본 단서가 나중에 바뀌지 않게, 보안 규칙도 같은 기준). 아직 공개 안 된 칸은 고칠 수 있고, 비어 있던 칸은 늦게라도 쓸 수 있다.
- 응모권: 미션 인증 1장(최대 3), 카드 추가분(보통 +1장, 도전 +2장, 3주차 카드 포함 합계 최대 6), 비용 카드 +1장(한 번만), 받는 사람 인증 입력 1장(최대 3), 끝까지 안 들킴 2장, 정답 지목 1장, 우승 파트 1장, 수호천사(지원자만) 1장씩(최대 2). 최대 17장이고, 수호천사로 연결된 지원자만 +2장으로 19장.
  - 은신 2장은 **내 미션 3건이 모두 인증(또는 인정)되고, 프로필 6문항을 다 채워 단서 6개가 대상에게 간 마니또만** 받는다(`hiddenMinMissions`, `hiddenNeedsClues`). 1주만 하고 쉬어도 은신 2장이 붙던 것을 막으려고 3건으로 올렸다(예전에는 1건). 우승 파트 +1과 못 받은 주차 보상의 조건은 그대로 "내 미션 1건 이상"이다. 대상 불참이나 운영자 "받았음" 확인으로 인정된 미션도 3건에 센다. 내 미션 화면의 "끝까지 해야 받는 응모권" 줄이 남은 건수와 놓치는 장수를 보여 준다.
  - 카드 추가분은 **받는 사람이 직접 인증했고, 마니또가 고른 카드를 보고 같다고 확인한 미션에만** 붙는다(`cardMatch: true`. 확인이 없거나 "카드와 다름"이면 없다). 카드 난이도는 실제 카드 목록(`MISSION_CARDS`)의 번호·난이도·글과 맞는 것만 인정한다(쉬운 카드를 도전이라고 적어 저장해도 0장). 대상 불참이나 운영자 확인으로 인정된 미션은 미션 응모권 1장만 받는다.
  - 상대방 때문에 손해 보지 않게: ① 내 마니또가 미션을 안 보낸 주차, 그리고 완료를 알렸지만 운영자가 "못 받음"으로 확인한 주차는 인증 입력 대신 1장(인증 입력과 합쳐 최대 3장, 내 미션이 1건 이상 인증된 사람만). ② 받는 사람의 유효한 인증이 없는 미션도 다음 경우에는 마니또의 미션으로 인정한다(카드 추가분은 없음): 운영자가 "받았음"으로 확인(인증이 없을 때도, 인증이 무효 처리됐을 때도), 대상이 불참(가입 안 함·중도 이탈), **사이트가 전달한 3주차 칭찬 카드**(운영자가 가리지 않은 것. 받는 사람이 마감 전에 인증하지 않아 마니또가 미션 1장과 은신 2장을 잃는 일을 막는다). 운영자의 확인이 먼저다: "못 받음"이면 불참이어도, 칭찬 카드여도 인정하지 않는다. 무효 처리된 인증은 "받았음" 확인이 없으면 인정하지 않는다. ③ 확인이 없는 미인증 주차(대상이 참여 중)는 마니또도 받는 사람도 받지 못한다. 그래서 집계 전에 "집계 전 확인" 표를 꼭 처리한다.
  - 가입 안 한 사람, 중도 이탈, 수상 제외는 0장(추첨 대상 아님).
  - 정체를 알려주면 둘의 합계가 1장 줄어드는 구조는 미션 3건이 모두 인정된 마니또에게만 성립한다. 3건을 못 채운 마니또는 잃을 은신이 없어서, 알려주면 받는 사람만 1장을 얻는다(확인되면 수상 제외로 대응).
- 파트 대항전: 파트별 미션 완수율로 순위를 매긴다.
  - 주간 순위("파트 순위" 탭): 파트원이 완료를 알린 미션 수 ÷ (가입한 파트 인원 × 열린 주차). 운영자가 "이번 주 단서 2개 공개"를 누를 때 같이 발표되고(`public/board` 문서), "파트 순위만 다시 발표"로 따로 갱신할 수도 있다. 미션 진행을 마감하고 최종 지목으로 넘길 때 마지막으로 한 번 더 발표된다. **실시간이 아니다.** 실시간이면 미션을 받은 직후 어느 파트 숫자가 올랐는지로 마니또의 파트가 드러난다.
  - 개인별 진행(누가 몇 개 했는지)은 본인과 운영자만 본다(보안 규칙). 참여자에게는 파트 합계만 보인다.
  - 최종 순위(집계): 받는 사람이 인증한(또는 운영자가 인정한) 미션 수 ÷ (가입한 파트 인원 × 3). 1위 파트(동률이면 모두)의 파트원은 응모권 +1장. **내 미션이 1건 이상 인증된 사람만** 받고, 불참·수상 제외는 받지 못한다. 불참자(가입 안 함·중도 이탈)는 파트 인원에서도 빠진다.
  - 한계: 주간 순위가 0%이거나 100%인 파트가 있으면 "미션을 받았으니 내 마니또는 0% 파트가 아니다" 같은 추리가 된다(파트 합계를 발표하는 한 피할 수 없음). 인원이 적은 파트는 한두 명에 따라 완수율이 크게 움직인다.
- 상품(`src/config/prizes.js`): 1등 대추첨 50만원 1명, 2등 베스트 마니또 10만원 3명, 3등 베스트 후기상 5만원 1명, 4등 5만원 4명, 5등 1만원 7명, 6등 커피 쿠폰(5천원) 20명. 1~5등 합계 112만원(선물대 한도, 세금 포함), 6등은 회의비로 따로. **참여자 규칙 탭에는 1등(50만원 상품권)만 금액·인원이 보이고 나머지는 "추후 공지"로 나온다**(`PRIZES_ANNOUNCED`. 확정해서 알릴 때 key를 더한다). 발표 화면과 결과 탭은 모두 보인다.
  - **2등 베스트 마니또는 응모권이 가장 많은 3명**이다(투표·운영진 평가는 없앴다). **동점이면 내 미션에 달린 후기가 남에게 받은 공감 수(`missionLikes`)가 많은 사람**, 그래도 같을 때만 현장 숫자로 가른다(`seededTop`). 1등으로 뽑힌 사람은 빠지고 다음 순위가 받는다.
- 시상·추첨(사용자가 정함): **한 사람은 하나만 받고, 겹치면 큰 상이 우선**이다(1등 > 2등 > 3등 > 4등 > 5등 > 6등). 최대한 많은 사람이 받게 하려는 것이다.
  - 1·4·5등은 **현장 종이 추첨**: 모두가 보는 앞에서 각자 응모권 수만큼 자기 이름 종이를 통에 넣고 직접 뽑는다. 운영자가 뽑힌 이름을 발표 화면에 입력한다.
  - 순서: 2등 → 3등 → 4등 → 5등 → 1등. 1등은 이미 다른 상을 받은 사람이 뽑혀도 1등이고, 그 사람이 받았던 자리는 다시 채운다(2등은 다음 순위, 3등은 다음 후기, 4·5등은 다시 뽑기).
  - 3등(공감 1위 후기)의 주인이 2등 수상자면 다음 순위 후기가 받는다. 집계할 때 공감 많은 순 후기 목록(`results/public.reviewRank`)을 저장해 둔다.
  - 6등은 인원이 많아 사이트가 뽑는다: 현장 숫자와 응모권 표로, 1~5등을 받은 사람을 빼고 응모권 수에 비례해(`drawOnline`). 결과 탭의 "6등 추첨 검증"이 누구 화면에서든 같은 계산을 다시 해서 비교한다(`verifyOnline`). 종이 추첨은 사이트가 검증할 수 없다(현장에서 모두가 지켜본다).
  - 투표는 없앴다(화면 `Vote.jsx`, 투표 집계 코드 삭제). 보안 규칙의 `votes`·`voteCards`·`voteViews`·`cardOwners`·`adminEval` 경로는 규칙을 다시 게시하지 않아도 되게 그대로 두었고(쓰는 화면이 없음), 다음에 규칙을 고칠 때 같이 지우면 된다. 단계 3은 "마감"으로 이름만 바꿨다(단계는 한 칸씩만 넘어가므로 번호는 그대로).
- 단계: 한 칸씩 앞으로만 넘어간다. 집계 결과가 없으면 공개 단계로 넘어갈 수 없다(화면과 보안 규칙).

- **수호천사**(응모권을 더 받고 싶은 사람이 지원): 마니또가 미션을 안 해서 아무것도 받지 못한 사람을 구한다.
  - 참여자가 내 미션 화면에서 "수호천사 지원하기"를 누른다(`angelVolunteers/{pid}`). 지원 버튼은 미션이 시작된 뒤에만 나온다(가입 기간에 먼저 가입한 사람이 앞서지 않게. 보안 규칙도 미션 진행 단계의 지원만 받는다). 지원 시각(`at`, 서버 시각)이 순서가 되고, 취소했다가 다시 지원하면 맨 뒤로 간다.
  - **누구를 연결할지는 운영자가 고르지 않는다. 먼저 지원한 순서대로 자동으로 연결된다**(`src/lib/angels.js`, `angels/{받는사람}`).
    - 언제: 운영자가 2주차·3주차를 열 때 자동으로(그 뒤에 지원자가 생기면 운영 탭 "지금 순서대로 연결"로 같은 기준을 다시 적용). 1주차 중에는 연결하지 않는다("아직 안 한 것"과 "안 하는 것"을 가를 수 없어서).
    - 누구에게: 그때까지 마니또의 완료 알림이 한 건도 없고, 가입했고 중도 이탈이 아닌 사람. 명단 순서대로.
    - 누가: 지원 시각이 가장 이른 사람. 단 받는 사람 본인, 그 사람의 마니또, 이미 다른 사람과 연결된 지원자, **닫힌 주차의 자기 마니또 미션을 다 하지 않은 지원자**(자기 대상은 챙기지 않으면서 수호천사 응모권만 받는 것 방지. 나중에 하면 그때부터 연결될 수 있다), 중도 이탈·수상 제외는 건너뛴다. 한 지원자는 한 사람에게만.
    - 보안 규칙은 "지원 중인 사람, 본인·그 사람의 마니또 아님"까지만 확인한다. 순서(먼저 지원한 사람)는 화면이 지키는 것이라, 운영 화면에 지원 순서·시각과 연결별 "지원 몇 번째"가 보이고 발표 화면 "숨은 수호천사"에도 몇 번째로 지원했는지 나온다.
  - 수호천사는 내 미션 화면의 "수호천사 미션"에서 그 사람에게 미션을 2번까지 하고 "완료 알리기"(`angelGifts/{받는사람}_{1|2}`, 보낸 사람 정보 없음). 그 사람의 알레르기 칸도 보인다.
  - 연결되면 수호천사에게 어느 탭에서나 "수호천사로 연결됐어요!" 팝업이 한 번 뜬다(미션 진행 단계, 받는 사람 이름은 팝업에 쓰지 않음, "수호천사 미션 보러 가기"를 누르면 내 미션의 수호천사 미션으로 간다. 이 기기에 기억해 다시 안 뜨고, 다른 기기에서는 한 번 더 뜬다). 이미 연결된 사람도 이 기능이 배포된 뒤 사이트를 열면 한 번 뜬다.
  - 받는 사람은 추리 보드 "수호천사가 보낸 것"에서 후기(10자 이상)와 함께 "받았어요". 누가 수호천사인지는 송년회 발표 화면 "숨은 수호천사"에서 공개된다.
  - 응모권: 확인된 수호천사 미션 1건마다 수호천사 +1장(최대 2). 받는 사람은 인증 입력으로 친다(못 받은 주차 보상과 합쳐 최대 3장이라 이중으로 받지 않는다). 수호천사 미션은 은신·보상·우승 파트 조건의 "내 미션 수"에는 들어가지 않는다.
  - 수호천사 미션이 한 번이라도 오면 연결을 바꾸거나 풀 수 없다(누구에게 응모권을 줄지 흔들리지 않게). 그 전에는 운영자가 "연결 풀고 다음 순번으로"를 누를 수 있다(수호천사가 연락이 안 되거나 못 하겠다고 한 경우). 넘긴 짝은 다시 연결되지 않고(`meta/angelSkips`), 풀린 지원자는 순서대로 다른 사람에게 연결될 수 있다. **운영자 판단이 남는 곳은 이 버튼을 누를지 말지뿐이다.**
- 소소한 재미(응모권과 무관):
  - **이번 주 할 일**: 내 미션 화면 맨 위에 지금 단계에서 아직 안 한 것(프로필, 이번 주 카드·완료 알리기, 받은 미션 인증, 이번 주 추측, 최종 지목)과 다음 일정이 보인다.
  - **내 마니또에게 알려 줄 것**(`prefs/{pid}`): 못 먹는 음식·알레르기, 좋아하는 간식, 받기 곤란한 것. 나를 맡은 마니또와 운영자만 읽는다. 마니또의 내 미션 화면에 "내 대상이 알려 준 것"으로 보이고 알레르기는 빨간 테두리로 표시된다.
  - **마니또에게 한마디**(`toManito/{받는사람}_{주차}`): 받는 사람이 마니또에게 주차마다 한 번 익명으로(고칠 수 없음, 200자). 받는 사람·그 마니또·운영자만 읽고, 운영자는 "쪽지 검토"에서 지울 수 있다. 미션 진행·최종 지목 단계에만.
  - **주차별 추측**(`midGuesses/{pid}`): 용의자 보드에서 열린 주차 칸에 "지금 가장 의심되는 사람"을 남긴다(그 주 안에는 바꿀 수 있음, 지난 주는 잠김). 맞았는지는 알려 주지 않는다. 집계 때 최종 지목이 맞은 사람 중 몇 주차부터 계속 맞혔는지(`noticedWeeks`)를 계산해 발표한다.
  - **피드 공감**(`feed.likes` + `feedLikes/{글ID}_{pid}`): 글마다 한 번, 취소 없음(쓰기 반복 방지). 누가 어느 글에 공감했는지는 본인·운영자만. 가린 글·무효 글에는 못 한다. 공감을 가장 많이 받은 후기가 3등 베스트 후기상이다(`pickBestReview`: 집계할 때 `feedLikes`를 읽어 자기 후기에 누른 공감은 빼고 센다. 피드 글에는 글쓴이가 없어서 보안 규칙으로는 자기 공감을 막을 수 없다. 동점이면 먼저 쓴 후기, 공감이 하나도 없으면 수상자 없음).
  - **안 읽은 표시**: 새 쪽지(추리 보드)·새 한마디(내 미션)가 오면 메뉴에 숫자, 브라우저 탭 제목에 "(n)". 본 것은 그 기기에만 기억한다(다른 기기에서는 처음에 다시 뜬다).

## 운영 도구

- **규칙 탭**: 참여자에게 응모권·상품·단서·비용·지켜야 할 것·누가 무엇을 볼 수 있는지를 보여 준다. 숫자는 `prizes.js`·`constants.js`에서 가져온다(`src/pages/Rules.jsx`). 문장으로 적은 규칙은 `src/lib/scoring.js`와 같아야 한다.
- **공지**: 운영 탭에서 올리면 모든 참여자 화면 위에 보인다(마감 안내 등).
- **공동 운영자**: 참여하지 않는 계정을 계정 번호로 지정한다(위 "운영자와 공동 운영자"). 운영자가 자리를 비워도 주차·단서·단계 진행이 멈추지 않게 한 명 이상 지정해 둘 것.
- **짝 현황**: 운영 탭에 누가 누구의 마니또인지와 주차별 상태(카드 고름, 인증 대기, 받은 게 없다고 신고, 받았음·못 받음 확인, 인증됨, 인증 무효), 추가 쪽지 수, 최종 지목(정답·오답)이 표로 나온다. 처음에는 접혀 있고 "짝 현황 보기"를 눌러야 펼쳐진다(어깨너머 보기 방지). "마니또가 낸 단서 보기"로 단서 열도 볼 수 있다.
- **매주 남긴 마니또 추측**: 참여자가 용의자 보드 아래에서 주차마다 남긴 추측. 주차마다 받는 중/마감, 남긴 인원/가입 인원(%), 맞힌 인원이 바로 보이고, "사람별 보기"를 누르면 누가 누구를 골랐는지(✔ = 실제 마니또)가 나온다(짝이 드러나니 화면 공유 때는 가릴 것). "운영 자료 불러오기"를 눌러야 읽는다. 지금 열린 주차만 남기거나 바꿀 수 있어서, 다음 주차가 열리면 그 주차 추측은 마감된다.
- **초대 코드·메일**: 명단과 계정 연결 표에서 초대 코드와 연결된 메일은 가려져 있고, "초대 코드·메일 보기"를 눌러야 보인다(처음 운영자만).
- **인증 검토**: 인증 무효 처리, 피드 글 가리기, 감사 답장 지우기, 글쓴이가 고친 횟수("고침 N번") 보기, "카드와 다름"·"카드 확인 전"(받는 사람이 완료 알림보다 먼저 인증해 카드를 아직 확인하지 않은 것)을 같음으로 고치기(두 사람에게 확인한 뒤, 확인창이 한 번 나온다). 무효 처리하면 받는 사람의 인증 응모권과 마니또의 그 미션 응모권이 빠진다. 후기만 문제였고 미션은 실제로 받았다면 "집계 전 확인"에서 "받았음"을 눌러 마니또의 미션은 인정할 수 있다.
- **쪽지 검토**: 신고된 쪽지가 먼저 나온다. 가리기, 추가 쪽지 삭제, 신고 처리 완료. 아래 "마니또에게 한마디 보기"에서 한마디를 지울 수 있다(지우면 그 주차에 다시 보낼 수 있다).
- **발표 화면**: 위 "송년회 발표 화면".
- **수호천사**: 지원 순서(시각, 상태: 연결됨·대기·자기 미션을 다 하지 않아 건너뜀), "도움이 필요한 사람" 목록, "지금 순서대로 연결"(주차를 열 때 자동으로 연결되므로 보통은 누를 일이 없다), 연결별 지원 순서·수호천사 미션·확인 현황, "연결 풀고 다음 순번으로". 고르는 칸은 없다.
- **쓰기 횟수**: 참여자가 고치는 문서에는 고칠 때마다 1씩 오르는 횟수(`n`)가 붙는다(보안 규칙이 정확히 1씩 오르는지 확인해서 빼거나 건너뛸 수 없다). 사이트가 무료 한도 소진으로 멈추면 "쓰기 횟수 보기"로 누가 일부러 반복했는지 찾는다. **읽기 반복은 기록할 방법이 없다**(아래 한계).
- **검산**: 집계 단계에서 저장된 응모권 표를 지금 자료로 다시 계산해 다른 사람이 있는지 보여 준다(운영자 한 명이 응모권 표를 고쳐 쓴 경우를 다른 운영자가 찾을 수 있게).
- **받은 게 없어요 신고**: 미션 진행~마감 단계에 신고된 주차가 표로 나온다. **신고만으로는 아무것도 바뀌지 않는다.** 두 사람에게 확인하고 "받았음" 또는 "못 받음"을 누른다(같은 버튼을 다시 누르면 취소). "못 받음"은 마니또가 그 미션의 응모권(과 3건을 못 채우면 은신)을 잃는 결정이라 **처음 운영자만** 확정할 수 있고, 누르면 결과를 알리는 확인창이 한 번 나온다(공동 운영자 화면에서는 버튼이 꺼져 있고, 보안 규칙도 공동 운영자의 "못 받음" 쓰기·취소를 거부한다).
- **최근 접속**: 미션 진행 현황 표에 사람별로 보인다(서버 시각으로만 저장돼 꾸밀 수 없다). 받은 미션을 인증하지 않으면 그 사람의 마니또가 응모권을 못 받으므로, 오래 안 들어온 사람은 따로 알려 준다. 참여자 화면에도 "아직 인증하지 않은 미션 n건" 알림이 뜬다.
- **중도 이탈**: 더 참여할 수 없게 된 사람을 표시한다. 본인은 0장, 그 사람의 마니또와 그 사람이 맡은 사람은 위 보완 규칙으로 처리된다.
- **집계 전 확인**: 집계 단계에서 "인증이 없는 완료 알림" 표가 나온다(신고가 없던 것 포함). 주차마다 "받았음" 또는 "못 받음"으로 처리하고 집계할 것. 처리하지 않은 주차는 어느 쪽에도 응모권이 생기지 않는다(대상이 불참이면 자동으로 마니또의 미션으로 인정). 3주차 칭찬 카드는 사이트가 전달한 것이라 받는 사람이 인증하지 않아도 자동으로 인정되어 표에 나오지 않는다("쪽지 검토"에서 가린 칭찬 카드는 나온다). 인증이 무효 처리된 주차도 표에 나오며, "받았음"을 누르면 마니또의 미션만 인정된다.
- **규칙 버전 경고**: 콘솔에 게시된 보안 규칙이 예전 것이면 운영 화면 맨 위에 경고가 뜬다. 그 상태에서는 인증·피드·배정이 거부되므로 바로 `firestore.rules`를 게시한다.

## 로그인과 같은 기기 사용

- 메일 주소 + 비밀번호로 로그인한다. 메일 주소는 본인의 연결 문서(`users/{uid}`)에만 저장돼 본인과 운영자만 볼 수 있다(다른 참여자는 못 봄). 내 프로필 화면에 로그인한 메일이, 운영 화면 명단·계정 연결 표에 이름별 "연결된 메일"이 표시된다. 규칙이 로그인한 계정의 메일과 같은 값만 받는다.
- 같은 기기를 여러 사람이 쓸 수 있다. 헤더에 지금 로그인한 사람이 "○○님 로그아웃"으로 보이고, 로그아웃 후 다른 사람이 자기 계정으로 로그인하면 된다. 사람이 바뀌면 화면 상태를 통째로 새로 만들어 앞 사람의 이름·데이터가 남지 않는다.
- 로그인 화면의 "이 기기에서 로그인 유지"는 **기본이 꺼짐**이라 탭을 닫으면 로그아웃된다(공용 PC·자리 비움 대비). 체크하면 로그아웃하기 전까지 유지되고, 그 기기에서는 체크 상태를 기억한다.
- 비밀번호는 8자 이상, 글자와 숫자를 섞어야 가입된다(화면에서 확인. Firebase 서버 쪽 비밀번호 정책은 이 저장소에서 설정하지 않았다). 로그인 화면에 "운영진은 비밀번호를 묻지 않아요" 안내가 있다.
- 내 미션 화면의 대상 이름과 캐릭터는 기본으로 가려져 있고 "보기"를 누르면 60초 동안 보인다(옆자리에서 화면을 보는 것 대비).
- 비밀번호를 잊으면 "비밀번호를 잊었어요" → 메일의 링크에서 새 비밀번호를 정한다.
- **계정 연결 해제**(운영 화면, 준비 단계는 명단 표 / 미션 시작 후는 "계정 연결" 표): 다른 사람이 초대 코드로 연결했거나, 메일을 잘못 적었거나, 비밀번호를 찾을 수 없을 때 쓴다. 누르면 그 계정은 "연결 전"으로 돌아가 아무것도 못 읽고, 초대 코드가 새로 바뀐다(예전 코드는 못 씀). 처음 운영자만 할 수 있고, 누르기 전에 **본인 확인을 얼굴 보고** 하라는 확인창이 뜬다(누군가 "제 계정 풀어 주세요"라고 사칭하는 경우 대비). 새 코드를 본인에게 전달하면 새 계정(또는 같은 계정)으로 다시 연결되고 프로필·미션·인증 기록은 이어진다. 용의자 보드에서 지운 표시만 초기화된다.

## 주차별 미션 마감

마니또의 카드 고르기·완료 알리기는 **지금 열린 주차만** 된다(보안 규칙). 다음 주차를 열면 그 전 주차가 마감된다: 1주차 11/24(화), 2주차 12/1(화), 3주차 12/8(화)(미션 마감, 그 뒤 최종 지목). 모두 11:00 마감으로 안내하고 다음 주차를 여는(3주차는 미션을 마감하는) 12:00에 실제로 닫힌다(그 사이에는 "마감 시각이 지났어요, 곧 닫혀요"). 지난 주차를 나중에 몰아서 할 수 없다. 완료한 주차의 "쪽지 더 보내기"와 **받은 미션 인증은 지난 주차도 된다**(인증은 최종 지목 마감까지). 운영 화면 "예약 (자동 진행)"에서 2·3주차 열기와 미션 마감을 일정표 시각(12:00)으로 예약할 수 있다(운영자 화면이 그 시각에 열려 있어야 그때 실행된다).

## 재촉 알림과 재촉 메일

사이트에는 서버가 없어서 휴대폰 알림(푸시)은 보낼 수 없다. 대신 두 가지를 둔다.

- **모두의 미션 진행**(참여 의지를 북돋기 위해, 11/24): 참여자 내 미션 탭 맨 위에 "K주차 미션 완료율 N%" 한 줄과 막대, 아래에 지난 주차 완료율과 "몇 시 기준"(아직 0%면 "첫 번째로 완료해 보세요!"). 아직 이번 주 미션을 안 한 사람의 "할 일" 줄에는 "벌써 참여자의 N%가 완료했어요!"가 붙는다. **몇 명 중 몇 명인지는 보이지 않는다**(사용자가 정함: 비율로만. 문서에도 완료율만 적어 참여자가 직접 읽어도 인원 수는 없다). 완료율 = 그 주차를 완료한 마니또 ÷ 가입한 사람. 운영자·공동 운영자 화면이 열려 있는 동안 5분마다 세어 `public/progress`에 적는다(서버가 없어서 운영자 화면이 하나도 열려 있지 않으면 숫자가 그대로 머문다). 부서 전체 비율만 보이고 파트별 숫자는 없다(실시간 파트 숫자로 마니또의 파트가 드러나지 않게).
- **사이트 안 "할 일"**: 참여자가 사이트를 열면 어느 탭에서나 맨 위에 뜬다. 열린 주차 중 아직 완료를 알리지 않은 미션(마니또로서), 내 마니또가 완료를 알렸는데 아직 인증하지 않은 미션(대상으로서), 이번 주 단서 2개가 공개된 뒤 아직 남기지 않은 이번 주차 추측(내 마니또가 누구일지. 그 주차가 닫힐 때까지 — 1주차는 11/24 12:00, 2주차는 12/1 12:00, 3주차는 12/8 12:00에 닫히고 안내는 미션과 같은 11:00). 버튼을 누르면 내 미션·추리 보드(용의자 보드)로 간다. 그 일을 하는 탭에서는 숨는다.
- **재촉 메일(운영 화면, 미션 진행·최종 지목 단계)**: "인증 안 한 대상"과 "미션 안 한 마니또"(미션 진행 단계만) 중에서 골라, 운영자의 회사 메일에서 숨은 참조로 보낸다. 가입 안 한 사람과 중도 이탈로 표시한 사람은 빠진다. 본문에는 이름·주차·누가 누구의 마니또인지를 적지 않는다. 화면에는 받는 사람 이름과 주차가 보인다.

가입 안내 메일은 미션 진행 단계 화면에서 뺐다(준비 단계 화면에만 있다).

## 백업과 되살리기

무료 요금제(Spark)에는 자동 백업이 없다. 운영 화면 맨 아래 "백업 내려받기" → "백업 만들기" → "전체 백업 파일 받기 (JSON)"으로 받아 둔다(하루 한 번 권장: 특히 단서 공개 날과 12/8 마감 직전. 한 번에 전체 문서 수만큼 읽는다). 파일에는 누가 누구의 마니또인지가 들어 있으니 다른 사람이 볼 수 없는 곳에 둔다.

자료가 지워졌을 때는 `tools/restore/restore_backup.py`로 되살린다. 사이트 안 버튼이 아닌 이유는 보안 규칙상 운영자 계정도 인증·피드 글·완료 표시 같은 대부분의 기록을 대신 쓸 수 없기 때문이다(서비스 계정 키로 규칙을 거치지 않고 쓴다).

1. Python 패키지 설치: `pip install -r tools/restore/requirements.txt` (google-cloud-firestore)
2. 서비스 계정 키: Firebase 콘솔 → 프로젝트 설정 → 서비스 계정 → "새 비공개 키 생성" → JSON 파일. **저장소에 올리거나 채팅·메일로 보내지 말 것.** 다 쓰면 콘솔에서 그 키를 지워도 된다.
3. 파일만 확인: `python3 tools/restore/restore_backup.py 백업.json`
4. 계획 보기(지금 DB와 비교, 쓰지 않음): `python3 tools/restore/restore_backup.py 백업.json --key 키.json` — 컬렉션마다 백업 수·없어진 수·내용이 다른 수·백업 뒤 생긴 수·쓸 수를 보여 준다.
5. 되살리기: 같은 명령에 `--apply`. 프로젝트 ID를 그대로 입력해야 진행한다.

- **아무것도 지우지 않는다.** 기본은 지금 DB에 없는 문서만 백업 값으로 다시 만든다(백업 뒤에 바뀐 문서·새로 생긴 문서는 그대로).
- `--overwrite`: 내용이 다른 문서도 백업 값으로 덮어쓴다(백업 뒤의 공감 수·진행 상황 등이 백업 시점으로 돌아간다). 그때도 설정(`config/app`: 단계·주차·단서 공개 수)은 `--include-config`를 붙여야 덮어쓴다.
- `--only roster,feed`: 일부 컬렉션만(설정은 `config/app`).
- 시각 값은 백업에 밀리초까지만 있어서 그 아래 자리는 0이 된다(순서에는 영향 없음).
- 읽기는 되살릴 컬렉션의 문서 수만큼(비교용), 쓰기는 되살리는 문서 수만큼 든다. 무료 한도가 이미 찬 날에는 한국 시간 오후 5시 이후에 실행한다.
- 검증: `e2e/restore.cjs`(에뮬레이터에서 백업 → 통째로 삭제 → 되살리기 → 문서가 백업과 하나하나 같은지, 옵션별 동작, 되살린 뒤 로그인해 화면 확인).

## 부서 공지용 결산 그림과 메일 글

주차 결산 공지(11/26 "1주차 결산 & 2주차 시작"처럼)에 쓸 그림(PNG)과 메일 글을 전체 백업 JSON에서 만든다(`tools/report/`). Firestore에 접속하지 않고 백업 파일만 읽는다.

```bash
node tools/report/report.mjs 백업.json --week 1 --out 결과폴더
```

- 결과: `report.png`(가로 `--width`, 기본 1400 — 메일 본문에서 보기 좋은 조금 넓은 비율 — 기준 2배, 배경에 눈), `report.html`, `report.json`(숫자), `mail.txt`(제목·본문. 신발장 사진 같은 것을 넣을 자리 `[사진 4장]`, 사이트 주소 자리 `[사이트 주소]`).
- 그림은 Playwright(Chromium)로 찍는다. 글꼴(Galmuri)은 jsDelivr에서 불러오고, 인터넷이 막힌 곳에서는 `--font-dir`로 글꼴 폴더(`npm pack galmuri@2.40.3`을 풀어 `package/dist`)를 준다.
- `--sample`: 예시 숫자로 모양만 본다(그림에 "예시 숫자 · 실제 아님" 띠가 붙는다).
- 숫자: 미션 완료율은 사이트의 "모두의 미션 진행"과 같은 식(완료 표시가 있는 마니또 ÷ 가입한 사람), 다음 주차 완료율(지금까지), 완료한 미션 중 대상이 인증한(무효 아님) 비율, 오간 쪽지 수(가린 것·빈 쪽지 제외), 피드 공감 합, 난이도·방법(실물/사이트 쪽지) 비율과 많이 고른 카드 3개, 주차별 추측 참여율(운영 화면 "매주 남긴 마니또 추측"과 같은 계산)과 맞힌 사람 수(0명이면 적지 않는다 — 추측한 사람 모두에게 "내 추측은 틀렸다"가 알려지므로), 공감 많은 후기 3건(익명 피드에 공개된 글, 가린 글·무효 글 제외, 줄이지 않고 줄바꿈까지 전문).
- 결과에는 이름·누가 누구의 마니또인지·파트별 숫자가 들어가지 않는다(`npm test`가 확인). 그래도 **후기 글 자체에 이름이 들어 있을 수 있으니 보내기 전에 읽어 본다.** 규칙 탭에서 아직 알리지 않은 2~6등 금액·인원과 칭호는 적지 않는다.

## 중도 이탈 처리 (짝 이어 붙이기)

참여자가 사정으로 빠지면 그 사람만 빼고 원을 이어 붙인다: X(빠지는 사람의 마니또) → Y(빠지는 사람) → Z(Y의 대상)에서 **X가 정한 주차부터 Z를 맡는다.** 미션이 시작된 뒤에는 보안 규칙상 운영자 계정도 짝·코드·단서를 바꿀 수 없어서, 되살리기와 같은 방식(서비스 계정 키)의 `tools/handover/handover.py`로 한다.

1. 사이트를 먼저 배포한다(지난 주차를 그 주차의 짝으로 계산하는 코드가 들어 있어야 한다). 쓰기 전에 백업을 받아 둔다.
2. Python 패키지·키: README "백업과 되살리기"의 1·2번과 같다(`pip install -r tools/restore/requirements.txt`, 서비스 계정 키 JSON).
3. 계획 보기(쓰지 않음): `python3 tools/handover/handover.py --key 키.json --leaver 이름` — 원래 원과 바뀐 뒤, 바뀌는 코드·단서(공개된 칸 표시)·명단을 모두 보여 준다. 같은 파트 짝이 되면 경고한다.
4. 적용: 같은 명령에 `--apply`(프로젝트 ID를 입력해야 진행). X가 이번 주차를 Y에게 이미 '완료'했으면 멈추고 둘 중 하나를 고르게 한다:
   - `--redo`: 그 완료를 되돌리고(완료 표시·완료 알림·추가 쪽지를 지우고 기록에 저장) X가 Z에게 이번 주차를 새로 한다.
   - `--from-slot 다음주차`: 그대로 두고 다음 주차부터 Z를 맡는다(그 주차의 X 미션은 대상 불참으로 인정, Z는 받지 못한 주차 보상).
5. 되돌리기: `--undo [--apply]`(가장 최근 것. X가 이어 받은 뒤 Z에게 완료했거나 Z가 인증했으면 멈춘다).

- 바뀌는 것: 짝, 코드(Y가 갖고 있던 Z 앞 코드를 X에게 — Z 쪽은 그대로), Z가 보는 단서 6칸(X의 답으로)과 파트 단서(X의 파트로), Y의 중도 이탈 표시와 추리 보드 후보에서 빼기. 바꾸기 전 값은 `meta/handover`와 실행한 폴더의 `handover-*.json`에 저장된다(누가 누구의 마니또인지가 들어 있으니 운영진만).
- 지난 주차는 원래 짝 기준으로 센다: X의 지난 주차는 Y에게 한 미션, Y가 한 주차는 Y의 미션(송년회에 오면 중도 이탈 표시를 풀면 응모권에 반영).
- **안내 팝업**: 스크립트가 X에게 "내 대상이 바뀌었어요", Z에게 "내 마니또가 바뀌었어요" 안내를 남기고(`notices`, 본인만 읽음), 두 사람이 사이트를 열면 팝업으로 한 번 뜬다(이름·파트는 쓰지 않는다 — Z에게 "같은 파트일 수 있다"를 알리면 마니또의 파트가 드러난다). 이미 사이트를 열어 둔 사람은 새로 고쳐야 바뀐 짝·단서·팝업이 보인다. 추리 보드는 모든 사람에게 내 파트를 후보에서 빼지 않고, 참여자 규칙에도 "같은 파트끼리는 마니또가 되지 않아요"를 적지 않는다(11/26부터 — 이어 붙인 짝이 같은 파트일 수 있어서. 배정은 여전히 다른 파트끼리).
- 검증: `e2e/handover.cjs`(에뮬레이터에서 4명·2개 파트로 적용·되돌리기·다시 적용·새 대상에게 다시 한 주차 인증·운영 화면 점검·최종 지목·집계).

## 완료 전 쪽지 (메뉴판·예고)

마니또 카페(메뉴판을 보내고 주문을 받아 배달)·타임어택(배달 시각 예고)처럼 미션 전에 사이트로 알릴 게 있는 카드는, 예전에는 글을 보내려면 '완료'를 눌러야 했다. 이제 지금 열린 주차는 카드를 고른 뒤 **"완료 전에 쪽지 먼저 보내기"**로 쪽지만 먼저 보낸다(보안 규칙 20261128 — **콘솔에 다시 게시해야 한다**). 이 쪽지에는 인증 코드가 실리지 않고(받기 전에 인증하지 않게), 쪽지 수는 "쪽지 더 보내기"와 합쳐 주마다 5건이다. 완료를 알린 주차가 아니므로 응모권·짝 현황·대상의 "받은 게 없어요"·인증 요청에는 영향이 없다. 이미 미리 '완료'를 누른 기록은 그대로다.

## 요금제(Spark·Blaze)와 예산

- **Spark(지금)**: 돈이 나가지 않는다. 대신 하루 무료 한도(읽기 5만·쓰기 2만·삭제 2만 건, 태평양 시간 자정 = 한국 시간 오후 5시쯤 초기화)를 넘으면 초기화될 때까지 프로젝트 전체의 그 작업이 거부된다(사이트가 멈춤). 저장된 자료는 그대로다.
- **Blaze(종량제)**: 같은 무료 한도가 그대로 있고 **넘은 만큼만** 낸다(읽기는 서울 등 지역 위치 기준 10만 건당 약 0.03달러, 다중 리전 위치는 더 비쌈). 한도 때문에 멈추지 않는다. 결제 수단(카드)이 필요하고, 요금 상한이 자동으로 걸리지 않는다.
- 예상(읽기만, 지역 위치 0.03달러/10만 건, 1달러 = 1,450원으로 셈, 11/20~12/9 20일, 부가세 별도): 하루 7만 건이면 하루 2만 건 초과 → 약 170원, 하루 10만 건이면 약 430원, 하루 20만 건이면 약 1,300원. 누가 읽기를 반복해 하루 100만 건이 되면 약 8,200원. 쓰기는 하루 수천 건 이하라 무료 한도 안이다.
- **예산은 알림이지 상한이 아니다**: Google Cloud 콘솔 → 결제 → 예산 및 알림 → 예산 만들기(범위: 이 프로젝트, 금액 예: 1,000원, 50%·100%에서 메일). 넘으면 메일만 오고 사용은 계속된다. 자동으로 멈추게 하려면 예산 알림(Pub/Sub)을 받아 결제를 끄는 함수를 따로 만들어야 하는데, 결제가 꺼지면 Blaze 기능이 멈추고 되돌리는 데 손이 가서 만들지 않았다.
- Blaze에서는 콘솔 Firestore "재해 복구"에서 특정 시점 복구(7일)와 예약 백업을 켤 수 있다. 다만 이 둘로 되살리면 **새 데이터베이스**로 만들어져(사이트는 `(default)`를 읽는다) 옮겨 담는 작업이 따로 필요하다. 그래서 위의 JSON 백업 + 되살리기 스크립트가 바로 쓰는 방법이고, 재해 복구는 그 백업마저 없을 때의 안전망이다.

## 무료 한도와 읽기 수

무료 요금제(Spark)는 Firestore 읽기에 하루 한도가 있다(알려진 값 5만 건, 한국 시간 오후 5시쯤 초기화). 넘으면 그날 남은 시간 동안 모두 데이터를 못 불러온다. 그래서 같은 내용을 덜 읽게 만들어 두었다(행사 규칙·화면 순서는 그대로).

- 명단: 참여자 화면은 54명 문서 대신 요약 문서 `public/roster` 1건(이름·근무지·파트)을 읽는다. 운영 탭을 열면 명단과 요약이 다를 때 자동으로 다시 쓴다(미션 시작 때도 한 번 더 씀). 운영 화면은 전체 명단을 그대로 읽는다.
- 캐릭터: 전원 것을 구독하지 않고 화면에 나온 사람 것만 읽고, 이 기기에 6시간 기억해 둔다(`localStorage` `manito:avatars`. 캐릭터 번호는 참여자 누구나 읽는 값이라 비밀이 아니다). 추리 보드는 후보(54명이면 약 45명)의 캐릭터를 보여서, 예전에는 휴대폰으로 사이트를 새로 열 때마다 그만큼 읽었다. 다른 사람이 캐릭터를 바꾸면 최대 6시간 늦게 보인다(내 캐릭터는 바로 바뀌고, 내 프로필은 내 것을 늘 새로 읽는다).
- 피드: `feed` 문서를 최근 30건씩, "더 보기"로 30건 더. 감사 답장·공감 수는 같은 문서에 들어 있어서 따로 읽지 않는다. **실시간으로 구독하지 않는다**: 열 때와 "새 글 확인"·"더 보기"를 누를 때만 읽는다(구독하면 누가 공감을 누를 때마다 피드를 열어 둔 사람 수만큼 읽기가 생긴다. 공감이 3등과 2등 동점 기준에 쓰여 많이 눌릴 수 있다). 내가 공감한 글 목록은 사이트를 열고 처음 피드에 들어올 때 한 번만(내가 공감한 수만큼) 읽는다.
- 집계: 공감 문서(`feedLikes`)를 통째로 읽지 않는다(모두가 모든 글에 공감하면 수천 건). 공감을 받은 후기마다 당사자 두 사람의 문서만 골라 읽고, "검산"은 공감 문서를 읽지 않는다.
- 받은 쪽지: 내 앞으로 온 완료 알림·쪽지는 로그인할 때 한 번 구독해서 내 미션·추리 보드·안 읽은 표시가 같이 쓴다(예전에는 화면마다 따로 읽었다). 마니또는 내 대상의 한마디(최대 3건)를 구독한다.
- 파트 순위: 발표 문서 `public/board` 1건과 내 진행 문서 1건만 읽는다(예전 "우리 팀" 탭은 팀원 수만큼 읽었다).
- 기기 저장소 캐시는 쓰지 않는다. 같은 기기를 여러 사람이 쓸 때 앞 사람 데이터가 기기에 남지 않게 하기 위해서다.

- 탭: 한 번 연 탭은 닫지 않고 숨겨 둔다(피드·결과 탭 제외). 예전에는 탭을 옮길 때마다 화면을 새로 만들면서 구독을 다시 열어 처음부터 다시 읽었다(11/18 실측으로 하루 읽기가 한도에 거의 닿음. 에뮬레이터 측정: 내 미션 탭 들어갈 때 구독·조회 27개, 운영 탭은 54명 기준 약 1,500건 → 다시 들어갈 때 0~1개).
- 피드 다시 들어가기: 피드 탭은 들어올 때마다 새로 만들어지지만, 3분 안에 다시 들어오면 읽어 둔 최근 글 목록을 쓴다(`src/lib/feedCache.js`). "새 글 확인"·"더 보기"는 새로 읽고, 내가 인증 후기·감사 답장을 보내면(운영자는 무효·가리기·답장 지우기) 이 기기에 읽어 둔 목록을 지워 바로 보이게 한다. 다른 사람의 새 글은 3분 뒤나 "새 글 확인"을 누르면 보인다.
- 운영 화면 가볍게 열기: 미션 기간에 운영 탭을 새로 열면 단계·공지·예약만 보이고, 짝 현황·인증 검토·집계처럼 컬렉션을 통째로 읽는 패널은 "운영 자료 불러오기"를 눌러야 읽는다(54명 기준 한 번에 약 750건). 피드만 보거나 예약만 확인할 때는 불러오지 않아도 된다.
- 피드 요약 문서 `public/feed`: 운영자 화면이 최근 글 30건과 공감 많은 글 6건을 한 문서에 모아 두고(바뀌면 10초 안에), 참여자는 피드를 열 때 그 1건과 그 뒤에 새로 올라온 글만 읽는다(예전에는 사람마다 36건). 운영자 화면이 열려 있지 않으면 요약이 오래될 수 있는데, 새 글과 요약 뒤에 글쓴이가 고친 글(`editedAt`)은 따로 읽어서 보이고(고친 글 조회는 보통 0건이라 읽기 1건), 공감 수·처음 쓴 감사 답장은 "새 글 확인"을 누르면 최신이 된다. 운영자가 글을 가리거나 무효로 하면 요약에도 바로 반영한다.
- 처음 열 때 구독이 두 번 열리던 것(11/20에 찾아 고침): 명단 요약을 기다리는 동안 예전 값(빈 명단)으로 화면이 한 번 그려져 구독을 모두 연 뒤, 곧바로 "불러오는 중"으로 바뀌며 구독을 닫고 다시 열었다. 운영 화면은 열 때마다 모든 컬렉션을 두 번, 참여자는 불러오는 순서에 따라 내 미션 탭을 두 번 읽었다(배포 빌드로 측정, 6명 기준 운영 화면 146건 → 74건, 참여자 내 미션 17건 → 13건).
- 인증 코드 점검(운영 화면): 코드 문서 162건을 읽어서 "인증 코드 점검하기"를 누를 때만 읽는다.
- 모두의 미션 진행(`public/progress`): 운영자 화면이 문서를 통째로 읽지 않고 개수만 세는 집계(count)로 센다(한 번에 열린 주차 수 + 1건, 화면이 보이는 동안 5분마다). 참여자는 그 1건을 구독한다(완료율이 바뀔 때만, 많아야 5분에 한 번 다시 읽힘).

운영 화면은 짝 현황 때문에 배정·코드·미션·인증·신고·지목을 전부 구독한다(54명 기준 한 번 열 때 수백 건). 운영자 계정이 몇 개뿐이라 한도에는 영향이 작지만, 운영 화면을 여러 기기에 계속 띄워 두지는 말 것.

코드로 계산한 추정치(측정값 아님): 사이트 한 번 열기 약 130건 → 약 20건(내 미션 화면 기준), 피드 열기 최대 약 340건 → 약 30건. 추리 보드는 후보 캐릭터 때문에 처음 열 때 후보 수만큼 더 읽는다. 행사 중에는 Firebase 콘솔 → Firestore → 사용량에서 하루 읽기 수를 확인할 것.

## 비밀 유지 범위와 한계

- 외부인: 설정값이 공개라 누구나 Firebase 계정을 만들 수는 있지만, 초대 코드로 명단에 연결되기 전에는 초대 코드 하나 확인 말고는 아무것도 읽을 수 없고(단계 정보·명단·피드·결과 포함. 운영자 목록이 든 `config/app`도 연결된 사람과 운영자만 읽는다) 아무것도 쓸 수 없다(보안 규칙, `npm run test:rules`로 확인). 사이트 화면·코드는 GitHub 저장소에 쓰기 권한이 있는 계정만 바꿀 수 있으니 GitHub 계정에 2단계 인증을 켜 둘 것.
- 참여자: 남의 배정·코드·단서·쪽지·인증 문서·진행 상황과 명단 원본(연결된 계정, 수상 제외·중도 이탈 표시)을 읽을 수 없다(보안 규칙). 익명 피드 글에는 받는 사람 정보가 저장돼 있지 않다.
- 운영자·공동 운영자: 참여하지 않는 계정이라 짝·코드·미션 진행·인증·신고·지목·주차별 추측·수호천사 연결과 미션·쪽지 내용·마니또에게 한마디·프로필 답·단서·내 마니또에게 알려 줄 것·공감 표시를 **언제든** 읽는다(쪽지 신고 처리와 거짓 단서 확인 때문). 운영자 계정은 명단에 연결할 수 없고, 명단에 연결된 계정은 운영자가 될 수 없다(보안 규칙). 운영 화면에는 짝이 그대로 보이므로 화면 공유·어깨너머 보기에 주의한다.
- 단, 다음은 막을 수 없다.
  - Firebase 콘솔에 접근할 수 있는 사람은 Firestore 데이터를 직접 볼 수 있다.
  - 운영자와 공동 운영자는 누가 누구의 마니또인지 안다. 운영자가 참여자에게 알려 주는 것은 기술적으로 막을 수 없다(믿을 수 있는 사람만 지정할 것).
  - 주간 파트 순위는 완료 표시로 센다. 완료 표시는 받는 사람에게 가는 완료 알림과 한 묶음으로만 저장되고 주차마다 한 번이라, 개발자 도구로도 "완료 알림을 보낸 수"보다 부풀릴 수 없다(실제로 했는지는 별개). 최종 순위와 응모권은 받는 사람의 인증으로 계산한다.  응모권 핵심(인증 코드 검증, 인증 없는 피드 글, 단계 건너뛰기·역행, 안 열린 주차의 인증·완료·카드 고르기, 미션 난이도 바꾸기)은 규칙으로 막았다. 난이도는 완료 표시를 했거나 그 슬롯 코드가 이미 인증되면 바꿀 수 없고, 3주차 칭찬 슬롯에는 칭찬 카드만 들어간다.
  - **읽기 반복으로 무료 한도 소진**: 연결된 참여자 한 명이 개발자 도구로 읽기를 수만 번 반복하면 그날 사이트 전체가 멈출 수 있다(하루 5만 건). 서버 코드 없이는 막을 수도, 누가 했는지 기록할 수도 없다. 쓰기 반복은 쓰기 횟수로 찾을 수 있다. 멈추면 한국 시간 오후 5시쯤 한도가 초기화될 때까지 기다리거나, 그날만 Blaze(종량제)로 올리는 방법뿐이다. App Check를 켜도 진짜 사이트 안에서 개발자 도구로 보내는 요청은 막지 못한다.
  - 운영자는 집계 단계에서 응모권 표를 직접 고쳐 쓸 수 있다(보안 규칙이 응모권 계산을 다시 할 수 없음). "검산"과 "추첨 검증"으로 다른 운영자·참여자가 확인할 수 있게 했지만, 막지는 못한다.
  - 추첨 숫자는 운영자·공동 운영자 누구나 넣을 수 있다. 보안 규칙은 "한 번만, 다섯 칸 전부, 같은 숫자로"까지만 확인하고 당첨자가 그 숫자로 계산한 것과 같은지는 확인하지 못한다(규칙으로는 추첨을 다시 계산할 수 없다). 화면을 거치지 않고 다른 당첨자를 써 넣으면 결과 탭의 "추첨 검증"이 다르다고 표시한다 — 막는 것이 아니라 드러나게 한 것이다. 숫자는 현장에서 참석자에게 받아 모두가 보는 앞에서 넣을 것.
  - 운영자 설정(`config/app`)이 아직 없을 때는 로그인한 누구든 그 문서를 만들어 첫 운영자가 될 수 있다(처음 설정을 위한 것). 사이트 주소를 알리기 전에 운영자 계정을 먼저 만들 것("처음 설정").
  - 카드 추가분은 받는 사람이 카드를 보고 "같았어요"라고 한 것을 믿는다. 난이도를 속여 저장하는 것(쉬운 카드를 도전이라고 적기)과 받는 사람이 카드를 보지 않은 채 붙는 것은 막았지만, 짝끼리 짜고 같다고 하는 것은 가려낼 수 없다.
  - 마니또가 하지 않은 미션을 완료로 알리거나 받은 것과 다른 것을 했다고 하는 것, 받는 사람이 받고도 안 받았다고 하는 것, 짝끼리 짜고 정체를 알려 주는 것, 실제로 건네는 모습을 보고 알아내는 것은 사이트가 가려낼 수 없다. 카드 확인·받은 게 없어요·운영자 확인으로 줄였을 뿐이다.
  - 아직 안 열린 주차의 코드도 마니또가 미리 쪽지에 적어 보낼 수는 있다. 인증은 그 주차가 열려야 된다.
  - 발표 화면의 "넘긴 장면까지만 보이기"는 화면에서만 하는 것이다. 공개 단계가 되면 참여자는 결과 문서 전체를 읽을 권한이 생기므로, 개발자 도구로 직접 읽으면 무대보다 먼저 결과를 볼 수 있다(재미를 깨는 것일 뿐 응모권·추첨에는 영향 없음). 추첨도 숫자를 넣는 순간 1~6등이 모두 저장되므로, 발표하는 몇 분 동안은 같은 방법으로 당첨자를 먼저 볼 수 있다(결과를 바꿀 수는 없다). 집계 단계까지는 참여자가 결과를 읽을 수 없다.
  - 받는 사람이 실제로 받고도 "받은 게 없어요"로 알리거나, 마니또가 하지 않은 미션을 완료로 알리는 것은 사이트가 가려낼 수 없다. 그래서 운영자가 두 사람에게 확인하고 주차별로 정하게 했다.
- 재배정용 메모(`meta/assignment`)는 다시 배정할 때 지울 문서 목록이다(코드·사람 목록).
- 배정 방식 값(`assignVer`·`partExcluded`·`siteMatched`)은 준비 단계에서만 바꿀 수 있다. 미션 중에 배정 회차를 바꿔 단서를 숨기는 것을 막는다.
- 받는 사람 기준 코드(`receiverCodes`)는 배정할 때 같이 쓴다. 보안 규칙이 "이 피드 글이 그 사람의 실제 인증에 딸린 것인지" 확인하는 데 쓰고, 참여자는 읽을 수 없다. 예전 방식으로 배정된 자료에는 이 문서가 없는데, 미션이 시작된 뒤 운영 화면을 열면 자동으로 채워 넣는다.
- 다시 배정하면 배정 회차(`config.assignVer`)가 올라간다. 단서는 지금 회차 것만 읽을 수 있어 예전 마니또의 답이 남지 않고, 새 마니또가 앱을 열 때(내 미션 화면) 자동으로 새 대상에게 단서를 다시 보낸다. 새 마니또가 앱을 열기 전에는 받는 사람 화면에 "아직 마니또가 프로필을 안 채웠어요"로 보인다.

## App Check (선택)

App Check를 켜면 이 사이트 밖에서 만든 스크립트(설정값만 복사해 간 것)가 Firestore에 요청하는 것을 막는다. 외부인은 이미 보안 규칙 때문에 아무것도 못 읽지만, 규칙이 "연결된 사람인지" 확인하려고 문서 1~2건을 읽고, **이 읽기는 요청이 거부돼도 과금(무료 한도 차감)된다**(Firebase 문서: 규칙의 `get()`·`exists()`). 한도를 일부러 소진하는 공격을 줄이는 용도다. 켜지 않아도 동작한다.

Firebase는 새로 붙일 때 reCAPTCHA v3보다 **reCAPTCHA Enterprise**를 권장한다. 코드는 기본이 Enterprise이고(`appCheckProvider = "enterprise"`), 예전 v3 키를 쓰려면 `"v3"`로 바꾼다.

1. Google Cloud 콘솔(같은 프로젝트) → reCAPTCHA(Fraud Defense) 화면에서 API를 사용 설정하라고 하면 사용 설정하고, **웹(Website) 유형** 키를 만든다. 도메인에 `계정명.github.io`를 넣는다(배포용 키에 `localhost`는 넣지 않는다). **"체크박스 문제 사용"은 끈다**(App Check는 점수 방식 키만 쓴다. 참여자에게 문제가 뜨지 않는다).
2. Firebase 콘솔 → 보안(Security) → App Check → 앱 탭에서 웹 앱을 **reCAPTCHA Enterprise**로 등록하고 1의 키를 넣는다.
3. `src/firebase.config.js`의 `appCheckSiteKey`에 같은 키를 넣고 `main`에 올린다(배포). 비워 두면 꺼진 채로 동작하고, `npm run dev:emu`에서는 켜지지 않는다.
4. 사내 PC·사내 와이파이 휴대폰에서 사이트를 써 본 뒤, App Check 화면의 요청 통계에서 "확인됨" 비율을 본다. **사내망에서 reCAPTCHA(`www.google.com`)가 막혀 있으면 "적용(enforce)"을 켜는 순간 사내에서 사이트가 멈춘다.** 확인된 뒤에만 Cloud Firestore와 Authentication에 "적용"을 켠다. 문제가 생기면 "적용"만 끄면 바로 돌아온다.

무료 사용량: reCAPTCHA Enterprise는 월 1만 건 평가까지 무료이고, 결제 계정이 없는 프로젝트는 점수 단계가 4개(0.1·0.3·0.7·0.9)로 제한된다(Firebase 문서 기준). 토큰을 새로 받을 때마다 평가 1건이다.

이 저장소에서 확인하지 못한 것: 실제 프로젝트에서 켰을 때의 동작, 사내망에서 reCAPTCHA가 열리는지, 54명이 쓸 때 월 평가 수. API 키의 HTTP 리퍼러 제한도 할 수 있지만, 브라우저 밖 스크립트는 리퍼러를 꾸밀 수 있어 효과가 작다(한다면 `계정명.github.io`와 `프로젝트ID.firebaseapp.com`을 넣고 로그인·비밀번호 재설정을 다시 확인할 것).

화면(필드 이름·버튼 문구)을 바꾸면 이 스크립트도 같이 고쳐야 한다. `account.cjs`의 콘솔 오류 3건은 일부러 틀린 비밀번호·없는 메일로 시험한 것이다.

에뮬레이터로는 확인할 수 없는 것(실제 프로젝트에서 직접 확인할 것):

1. 규칙 게시가 오류 없이 끝나는지
2. 사내 PC·사내 와이파이 휴대폰에서 가입과 데이터 읽기·쓰기가 되는지(위 "사내망 확인")
3. 실제 Firebase 프로젝트 설정값(`src/firebase.config.js`)으로 로그인·가입이 되는지
4. 테스트 계정 2~3개로 운영자 설정 → 명단 → 배정 → 가입 → 미션 완료 → 코드 입력 → 단서 공개가 되는지 (같은 흐름을 `npm run dev:emu`로 로컬에서 먼저 볼 수 있다)
5. 운영 화면 맨 위에 규칙 버전 경고가 뜨지 않는지(뜨면 `firestore.rules`를 다시 게시)

## 픽셀 아이콘

메뉴(탭)와 패널 제목 앞의 작은 그림은 16×16 픽셀 SVG다(`src/assets/icons/*.svg`). `tools/icons/make_icons.py` 안의 글자 격자(한 글자 = 한 픽셀)를 고친 뒤 `python3 tools/icons/make_icons.py`를 돌리면 다시 만들어진다. 패널 제목의 아이콘은 제목에 든 낱말로 고르고(`src/icons.jsx`의 `TITLE_ICONS`), 맞는 낱말이 없으면 아이콘 없이 나온다. 내 미션 화면의 "미션 스탬프"(3주 도장판)와 미션 카드(난이도 색 띠·별·받는 응모권), 응모권 표 모양도 이때 같이 넣었다(`src/styles.css`).

## 연말 장식

눈 내림, 전구 줄, 패널 제목의 호랑가시 잎, 로고의 산타 모자, 트리·선물, 선물 리본, 로그인 화면 파트장님·PL님의 크리스마스 꾸밈(`src/assets/xmas/leader1~4.png`: 와인색 산타 모자(금색 방울)와 지팡이 사탕, 엘프 모자와 선물 상자, 루돌프 뿔·사슴 귀·빨간 코와 코코아 머그, 산타 모자와 선물 자루, 모두 목도리)은 `src/xmas.jsx`, `src/xmas.css`, `src/assets/xmas/`에만 있다. 기본 색·테두리·버튼·대사창(방탈출 값)은 `styles.css`에서 바꾸지 않았다. 움직임 줄이기 설정을 켠 기기에서는 눈과 전구가 멈춰 있다.

꾸밈 그림은 `tools/xmas/deco.py`(원본 `public/char/boss1~4.png` 위에 1픽셀 해상도로 그림, 모자는 원본의 머리 실루엣을 재서 폭·위치·높이를 맞추고 챙은 머리를 감싸는 곡선, 손 픽셀을 다시 덮어 소품을 쥔 모양)로 만들고, `tools/xmas/export_cards.py`가 사람별 PNG(투명 원본, 4배 확대, 1080×1920 크리스마스 배경 카드)를 내보낸다. Python과 Pillow가 필요하다.

```
python3 tools/xmas/deco.py public/char <출력 폴더>          # leader1~4.png
python3 tools/xmas/export_cards.py <출력 폴더> <내보낼 폴더>  # xmas1_santa.png, _x4.png, _card.png …
```

시즌이 끝나면 `src/main.jsx`의 xmas import 두 줄과 `<Snow />`, `src/App.jsx`의 `<Garland />`·`<XmasFooter />`, `src/pages/Login.jsx`의 장식 몇 줄(`Garland`, `XmasTree`, `Gifts`, `logo-xmas`)을 지우고, 로그인 화면 캐릭터를 `XMAS_LEADERS` 대신 원본 `public/char/boss1~4.png`로 바꾸면 원래 디자인으로 돌아간다.

## 운영자 계정 만들기 버튼

로그인 화면의 "운영자·공동 운영자 계정 만들기"는 사이트 주소 끝에 `?setup`을 붙여 들어갔을 때만 보인다(예: `https://jeehee1067-debug.github.io/manito-site/?setup`). 아직 운영자가 없는 프로젝트에서는 이 계정이 첫 운영자가 된다. 이미 운영자가 있으면 보안 규칙이 막아서 운영자가 되지 않고, 계정만 만들어져 "연결 전" 화면(계정 번호)으로 간다. 그 번호를 운영자가 "공동 운영자"에 넣어야 운영 권한이 생긴다.

## 상품 바꾸기

`src/config/prizes.js`만 고치면 규칙 안내·결과 화면·발표 화면의 상 이름·인원과 추첨이 같이 바뀐다(인원을 줄일 때는 `count`만 고치면 된다). 응모권 규칙(`TICKET_RULES`)도 같은 파일에 있다. 등수 이름은 `label`의 첫 낱말("4등")을 화면이 그대로 쓴다.
